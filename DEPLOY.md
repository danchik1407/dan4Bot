# Деплой AURA GAME: ровно два сервиса Render

Проект обслуживают **два** Web Service в Render. Третий (`dan4Bot-1`) удалён —
в коде нет ссылок на другие домены, а вся логика разложена так:

| Сервис | Что запускает | Чем занимается |
|---|---|---|
| **aura-api** | `uvicorn api:app --host 0.0.0.0 --port $PORT` | FastAPI: все игры, экономика, сундуки, магазин, апгрейд **и раздача Mini App** (`/miniapp` → `index.html`, `app.js`, `style.css`, картинки) |
| **dan4Bot** | `python bot.py` | aiogram (long polling): команды бота. Веб-сервер поднимается только формально (`start_fake_website`), чтобы Render видел открытый порт |

Оба сервиса используют **одну и ту же базу Supabase**, поэтому баланс в боте и в
Mini App — это одна запись (`users.coins`), синхронизация не нужна.

---

## 1. aura-api (Web Service)

- **Build Command:** `pip install -r requirements.txt`
- **Start Command:** `uvicorn api:app --host 0.0.0.0 --port $PORT`
- **Health Check Path:** `/api/health`
- **Environment:**
  - `SUPABASE_URL`
  - `SUPABASE_KEY`
  - `BOT_TOKEN`
  - `MAINTENANCE_MODE=1` — включить техработы обратно (по умолчанию **выключены**:
    играют все; с `=1` играют только `ADMIN_IDS`, остальные видят экран
    «Технические работы» и получают 403 от API).
  - Апгрейд техработы **не открывают**: он отдельно закрыт списком `ADMIN_IDS`
    (`UPGRADE_ADMIN_ONLY = True` в `api.py`) — пока админы, потом флаг в `False`.
- **Адреса:**
  - Mini App: `https://aura-api-mptt.onrender.com/miniapp/`
  - Корень `/` делает 307-редирект на `/miniapp/`
  - API: `https://aura-api-mptt.onrender.com/api/...`

Статика монтируется в `api.py`:

```python
BASE_DIR = os.path.dirname(os.path.abspath(__file__))
MINIAPP_DIR = os.path.join(BASE_DIR, "miniapp")
app.mount("/miniapp", StaticFiles(directory=MINIAPP_DIR, html=True), name="miniapp")
```

CORS открыт (`allow_origins=["*"]`): в WebView Telegram Origin бывает
`https://web.telegram.org`, `t.me` или отсутствует. Куки не используются —
авторизация только через подписанный `initData`.

## 2. dan4Bot (Web Service)

- **Build Command:** `pip install -r requirements.txt`
- **Start Command:** `python bot.py`
- **Environment:**
  - `BOT_TOKEN`
  - `SUPABASE_URL`
  - `SUPABASE_KEY`
  - (необязательно) `KEEPWARM=1` — прогрев `aura-api` по таймеру (см. §3.9;
    по умолчанию прогрев только «по активности в боте», чтобы не выйти за
    750 бесплатных часов Render)
  - (необязательно) `KEEPWARM_INTERVAL=240` — период прогрева, секунд
  - (необязательно) `KEEPWARM_SELF=1` — самопинг бота, чтобы он не засыпал
    (нужен `RENDER_EXTERNAL_URL` или `AURA_SELF_URL`)
  - (необязательно) `AURA_API_URL` — по умолчанию `https://aura-api-mptt.onrender.com`
  - (необязательно) `AURA_WEBAPP_URL` — по умолчанию `AURA_API_URL + "/miniapp/"`
  - (необязательно) `MINIAPP_SHORT_NAME` — короткое имя из BotFather (по умолчанию `Auragame`)
  - (необязательно) `MINIAPP_URL` — если нужно жёстко задать прямую ссылку `t.me/<бот>/<short_name>`
  - (необязательно) `BOT_USERNAME` — имя бота без `@`; по умолчанию берётся у Telegram при старте
  - Render сам добавляет `PORT` — его слушает `start_fake_website`

## 3. BotFather

`Configure Mini App` → **Web App URL** должен быть
`https://aura-api-mptt.onrender.com/miniapp/` (то есть `WEBAPP_URL` из `bot.py`).
`short_name` (`Auragame`) даёт прямую ссылку `https://t.me/<ваш_бот>/Auragame`.

**Команд `!апка` и `!апгрейд` больше нет (задача 20):**

Mini App открывается только кнопкой меню бота (BotFather → `Configure Mini App`),
а не командой в чате. Внутри бота ссылка собирается так же безопасно:

1. В личке — кнопка `web_app` с адресом `miniapp_webapp_url()` (это
   `https://aura-api-mptt.onrender.com/miniapp/`). Telegram открывает приложение
   сам и передаёт `initData`; короткое имя тут не участвует.
2. В группе Telegram **запрещает** кнопки `web_app`, поэтому там годится
   кнопка-ссылка `t.me/<бот>/<short_name>` — она открывает Mini App **внутри
   Telegram**, а не в браузере. `<бот>` подставляется из `get_me()` при старте.

Прямую ссылку `…onrender.com/miniapp/` игрокам отправлять нельзя: вне Telegram
не передаётся `initData`, и человек видит «технические работы» или пустой экран.
Ссылка `t.me/…` осталась только в админском `!сервисы` («Ссылка для игроков»).

Если в BotFather `short_name` не `Auragame` — задайте `MINIAPP_SHORT_NAME` в
сервисе dan4Bot или `MINIAPP_URL` целиком; перезапуск бота применит значение.

## 3.1. Если видите «Not Found»

`Not Found` — это ответ 404. Ниже все места, где он раньше появлялся, и что теперь:

| Что было не так | Было | Стало |
|---|---|---|
| В BotFather указан корень сервиса (без `/miniapp/`) | `Not Found` | 307 → `/miniapp/` |
| В BotFather указан `/index.html`, `/app.js`, `/style.css` | `Not Found` | 307 → `/miniapp/<файл>` |
| В BotFather указан адрес сервиса **dan4Bot** | `Not Found` | редирект в Mini App на aura-api |
| Имя Web Service в Render ≠ адреса в коде (`aura-api-mppt` / `aura-api-mptt`) | Render отвечает 404 на весь домен | клиент сам находит живой `/api/health`, бот на старте пишет рабочий адрес в лог |
| Запрос к `/api/...` несуществующего сервиса | `{"detail":"Not Found"}` | то же, но в `!сервисы` видно «❌ 404 Not Found» и подсказка про `AURA_API_URL` |
| Открыли `/webapp`, `/main` и т.п. | `Not Found` | 404 с подсказкой: где Mini App, где `/api/health`, где `/api/docs` |

Проверка адресов (в браузере или терминале):

```bash
curl -s https://<сервис>.onrender.com/api/health        # {"ok":true,"service":"aura-api",...}
curl -sI https://<сервис>.onrender.com/                 # 307 → /miniapp/
curl -sI https://<сервис>.onrender.com/index.html       # 307 → /miniapp/index.html
```

В боте (админ): `!сервисы` — покажет `✅ онлайн` или `❌ 404 Not Found` с причиной.
Если нужного домена нет в коде — задайте переменную `AURA_API_URL` в сервисе dan4Bot,
перезапуск не требуется для клиента: он всё равно возьмёт origin страницы `/miniapp/`.

## 4. Как проверить, что всё на двух сервисах

1. В боте (админ): `!сервисы` — покажет статус `aura-api` (`/api/health`),
   адрес API, адрес Mini App и подтверждение, что второй сервис — сам бот.
2. В браузере: `https://aura-api-mptt.onrender.com/api/health` →
   `{"ok": true, "status": "alive", "service": "aura-api", ...}`.
   То же самое отдаёт короткий алиас `/health` и `/` — их удобно ставить
   в UptimeRobot (см. §3.10).
3. `https://aura-api-mptt.onrender.com/miniapp/` — открывается Mini App
   (без Telegram покажет экран техработ: `initData` отсутствует — это норма).
4. `https://aura-api-mptt.onrender.com/` — в браузере редирект на `/miniapp/`,
   а для монитора (`Accept: */*`, так ходит UptimeRobot) — тот же
   `{"ok": true, "status": "alive", ...}`.

## 3.9. «SERVICE WAKING UP / START BUILDING ON RENDER TODAY» вместо игры

**Что это.** Это **страница самого Render**, а не наш код и не Mini App. Так
выглядит **просыпающийся** бесплатный Web Service: Render усыпляет free-инстанс
после **15 минут без входящих запросов**, а первый запрос ждёт ~1 минуту. Всё это
время браузер/Telegram показывает этот экран — до нашего `index.html` дело не
доходит.

Проверить причину за 5 секунд: открыть `https://aura-api-mptt.onrender.com/api/ping`.

- ответ сразу → сервис спит/не спит видно по `uptime_seconds` (маленькое число =
  только что проснулся);
- ответ через ~минуту → сервис спал. Это не баг, это лимит тарифа.

**Что уже сделано в коде (бесплатно, без правок настроек):**

| Механизм | Когда работает | Что даёт |
|---|---|---|
| `/api/ping` в `api.py` | всегда | дешёвый эндпоинт прогрева (ни базы, ни тиража) |
| `WarmApiMiddleware` в `bot.py` | любое действие в боте | бот будит `aura-api` **до** того, как игрок откроет Mini App |
| сердцебиение в `app.js` | пока аппка открыта | пинг каждые 4 минуты: сервис не успевает уснуть между экранами |

Строка `!сервисы` → «♻️ Прогрев: ✅ aura-api отвечал N с назад» показывает, что
механизм реально работает.

**Если экран всё ещё вылезает** — значит сервис спал, пока в боте было тихо.
Тогда есть три варианта:

1. **Держать `aura-api` тёплым постоянно (бесплатно).** Внешний cron
   (cron-job.org, UptimeRobot, GitHub Actions) раз в 5 минут запрашивает
   `https://aura-api-mptt.onrender.com/api/ping`. Это ~730 инстанс-часов в месяц
   из 750 бесплатных — влезает.
2. **Таймер из бота:** в `dan4Bot` добавить `KEEPWARM=1` (интервал —
   `KEEPWARM_INTERVAL=240`). Минус: пока бот живёт, он держит и API, а два
   всегда-включённых сервиса — это ~1460 ч/мес, то есть **выход за 750
   бесплатных часов** и приостановка сервисов до 1 числа. Поэтому по умолчанию
   выключено.
3. **Платный инстанс** ($7/мес, Starter) у `aura-api` — сон исчезает совсем.

Дополнительно: `KEEPWARM_SELF=1` заставляет бота пинговать самого себя
(`RENDER_EXTERNAL_URL`/`AURA_SELF_URL` + `/health`). Это лечит другую беду — «бот
молчит»: бот на long polling тоже усыпляется, потому что исходящие запросы к
Telegram Render за входящие не считает. Но по часам это тот самый вариант 2.

## 3.10. UptimeRobot: чтобы `aura-api` не засыпал (и не показывал «Down»)

Бесплатный Web Service на Render спит после **15 минут** без входящих запросов.
Внешний пинг раз в 5 минут держит сервис тёплым (~730 ч/мес из 750 бесплатных).
Подойдёт любой монитор с GET-запросами; ниже — UptimeRobot (бесплатный тариф
даёт 5-минутный интервал).

1. uptimerobot.com → **Add New Monitor**.
2. **Monitor Type**: `HTTP(s)`.
3. **Friendly Name**: `aura-api`.
4. **URL**: `https://aura-api-mptt.onrender.com/api/health`
   (подойдут также `/health` — тот же ответ, `/` — для монитора отдаёт этот же
   JSON, или `/api/ping` — ещё дешевле, без обращения к базе).
5. **Monitoring Interval**: `5 minutes`.
6. **Advanced → Keyword**: тип `exists`, значение `alive`.
   Так монитор краснеет не только когда сервис лежит, но и когда он отдаёт
   что-то постороннее.
7. **Create Monitor**.

Что должно быть в ответе:

```json
{"ok": true, "status": "alive", "service": "aura-api", "awake": {"uptime_seconds": 120, "just_woke": true}}
```

Важно: пинговать надо **тот сервис, который будит игрок**, — `aura-api`
(статика + API). Сам бот `dan4Bot` работает на long polling: его Render тоже
усыпляет, и лечится это либо `KEEPWARM_SELF=1` (§3.9, вариант 2), либо вторым
монитором на `https://<bot>.onrender.com/health`. Второй монитор = второй
всегда-живой сервис ≈1460 ч/мес, поэтому по умолчанию мы держим только
`aura-api`.

Если монитор показывает **Down** через минуту-две после создания — это не
ошибка: первый запрос будит инстанс, и UptimeRobot получает таймаут. Второй
запрос через 5 минут уже проходит.

## 4.0. Ошибка RLS при создании промокода

`new row violates row-level security policy for table "promocodes"` — в Supabase
включён RLS, а политик для серверной роли нет. Два способа лечения:

1. **Быстро, без правки базы:** добавить в сервисы `aura-api` и `dan4Bot`
   переменную `SUPABASE_SERVICE_KEY` = service_role key (Supabase → Settings → API).
   Код уже поддерживает её (`bot.py`, `api.py`).
2. **Миграцией:** применить `supabase/migrations/20261101000000_server_rls_policies.sql`
   (создаёт политики `*_server_all` для promocodes, promocode_uses, chest_claims,
   capsule_stock, upgrade_log, crash_history, bans) и выполнить
   `NOTIFY pgrst, 'reload schema';`.

Бот теперь показывает причину и подсказку прямо в чате, а не только в логах Render.

## 4.1. Сундуки: рулетка и «Сундуки обновляются»

**Анимация.** После нажатия «Открыть» сначала идёт белая вспышка ровно 1 секунда,
затем полоса предметов в стиле кейсов CS (`.roulette-container`): ячейки едут
справа налево ~6 секунд с плавным торможением, на каждой пройденной ячейке —
щелчок, по центру золотая метка. Выигрышная ячейка встаёт ровно под метку и
подсвечивается, ещё через 0.7 с открывается окно «Забрать». Награда начисляется
только по кнопке «Забрать» (`/api/claim_chest`), до этого баланс не меняется.

**Обычная капсула из сундука (задача 22).** Кроме коинов и ключа сундук может
выдать 💊 обычную капсулу — отдельным броском, **в добавок** к остальной награде:

| Сундук | Шанс капсулы | Откуда берётся |
|---|---|---|
| Обычный | **0.1 %** | `CHEST_CAPSULE_CHANCE_NORMAL` в `api.py` |
| Золотой | **10 %** | `CHEST_CAPSULE_CHANCE_GOLD` в `api.py` |

Клиент те же числа держит в `CHEST_CAPSULE_CHANCE_NORMAL/GOLD` в `miniapp/app.js`
(по ним рисуется лента рулетки) и печатает шанс под карточкой сундука. Проверить
можно по `/api/health` → `chests.normal.capsule_chance` / `chests.gold.capsule_chance`,
а в боте — `!сервисы` (строка «💊 капсула: обычный 0.1%, золотой 10%»).
Капсула, как и коины, начисляется **только по кнопке «Забрать»**.

> Чтобы капсула переживала перезапуск Render, примените
> `supabase/migrations/20261108000000_chest_capsule_reward.sql` (колонки
> `reward_item`, `reward_item_amount` + новые `chest_claim_*`). Без неё игра
> работает: капсула ждёт «Забрать» в памяти процесса и **пропадёт**, если сервис
> перезапустится до нажатия кнопки.

**Сундук открывается даже при сломанной таблице, но награда всё равно ждёт кнопку.**
Если `chest_claims` недоступна (нет таблицы, включён RLS, устарел кэш PostgREST),
сервер не отвечает 503 и **не начисляет коины сразу**: награда кладётся в память
процесса под id вида `mem-1a2b3c4d5e6f` и выдаётся тем же `/api/claim_chest`.
Ни при каком сценарии баланс не меняется до нажатия «Забрать». В логах:

```
ОШИБКА СУНДУКА: chest_claims недоступна → награда ждёт «Забрать» в памяти user_id=…: …
СУНДУК: награда отложена в памяти user_id=… claim=mem-1a2b3c4d5e6f (+13 коинов, +0 ключей)
СУНДУК: награда забрана из памяти user_id=… +13 коинов, +0 ключей
```

> Ограничение: память живёт до перезапуска Render (`TTL 12 часов`). Если награда
> ещё не забрана, а сервис перезапустился, `/api/claim_chest` ответит `404
> «Награда не найдена (сервер перезапускался). Открой сундук ещё раз»`. Поэтому
> таблица `chest_claims` остаётся основным путём — миграции обязательны.

Чтобы вернуть правильную схему «награда только по кнопке Забрать», примените обе
миграции и перезагрузите кэш схемы:

```sql
-- Supabase → SQL Editor
-- 20261030000000_capsule_stock_promo_types.sql   (сама таблица chest_claims)
-- 20261102000000_stock_and_chest_rpc.sql         (функции chest_claim_*: работают и при RLS)
NOTIFY pgrst, 'reload schema';
```

Проверить: `https://<сервис>/api/chest_ready` (или `!сервисы` в боте) — поле
`rpc_ready: true` означает, что функции на месте и награда снова выдаётся по «Забрать».

## 4.2.0. Тираж ВКЛЮЧЁН: все капсулы лимитированные

Задача 19: в `shop_catalog.py` стоит

```python
STOCK_LIMITS_ENABLED = True    # False — вернуть «бесконечные» капсулы
```

Тиражи (общие на всех игроков, `total_limit` в `SHOP_ITEMS`):

| Капсула | id | Тираж |
|---|---|---|
| Обычная 💊 | `capsule` | 1000 |
| Уникальная ⚱️ | `uniq_capsule` | 500 |
| Рубиновая ♦️ | `ruby` | 100 |
| Алмазная 💎 | `diamond` | 50 |
| Галактическая 🌌 | `galactic` | 10 |

Дневные лимиты выключены отдельным флагом `DAILY_LIMITS_ENABLED = False`:
ограничение только общим тиражом, «лимит N/день» нигде не показывается.
Включить обратно — поставить `True` и перезапустить `aura-api` + `dan4Bot`.

Что это значит на практике:

- в карточке магазина снова есть «Осталось: X из Y»;
- тираж списывается **до** баланса одной атомарной SQL-функцией
  `shop_take_stock` (SECURITY DEFINER), поэтому две одновременные покупки не
  продают одну капсулу дважды;
- когда строка тиража кончается (`stock = 0`), карточка исчезает с витрины, а
  покупка отвечает `400 Товар распродан`; если распродано ВСЁ, витрина пишет
  «Всё распродано», а не «Магазин пуст»;
- если записать тираж не удалось (нет миграции / RLS), магазин **не врёт**:
  покупка проходит, но в ответе `stock_ready: false`, `stock_warning` и в карточке
  «Остаток уточняется» — цифру полного тиража вместо реального остатка больше
  не покажем;
- при первом же чтении стока (`/api/shop_items`, `/api/health`, покупка) сервер
  сам добивает недостающие строки тиража (`shop_stock_snapshot` →
  `ensure_stock_rows`), поэтому «нет строки → распродан» больше не случается.

### 4.2.0.1. Что применить в Supabase (один файл, можно повторно)

```
supabase/migrations/20261106000000_stock_limits_on.sql
```

Он создаёт таблицу `capsule_stock`, добивает строки всех пяти капсул, приводит
`total` к тиражам каталога (проданное не возвращает — `stock` только обрезается
до `total`), пересоздаёт `shop_take_stock` / `shop_return_stock` /
`shop_stock_list` с `SECURITY DEFINER`, удаляет старую одноаргументную версию
`shop_take_stock`, выдаёт гранты и политику RLS, печатает таблицу остатков и
делает `NOTIFY pgrst, 'reload schema'`.

Проверка после деплоя:

1. `https://<сервис>/api/health` → `shop_stock.limits_enabled: true`,
   `shop_stock.ready: true`, `shop_stock.left` с ненулевыми остатками,
   `shop_stock.missing_rows: []`;
2. `https://<сервис>/api/stock_debug` → видно, какая сигнатура RPC отвечает и что
   лежит в таблице;
3. в боте (админ): `!сервисы` → строка «🎟️ Тираж: ✅ …», `!магазин` → у каждой
   капсулы «осталось X из Y»;
4. покупка в Mini App уменьшает счётчик на 1, при остатке 1 после покупки
   карточка исчезает.

**Открытие игры для всех (задача 21):** `MAINTENANCE_MODE` по умолчанию
выключен — играют все, апгрейд остаётся только за админами. Тиражи к открытию
обнуляются файлом `supabase/migrations/20261107000000_open_launch_promo_rls_and_stock_reset.sql`
(он же лечит RLS у `promocodes`: ошибка `42501 new row violates row-level
security policy for table "promocodes"`). Там же витрина стала одинаковой для
всех: `ruby`, `diamond`, `galactic` больше не `admin_only` — обычный игрок видит
все 5 капсул с тиражами.

**Если счётчик не двигается:** почти всегда не применён
`20261106000000_stock_limits_on.sql` (нет RPC или RLS режет `UPDATE`). В логах
Render это видно строкой `ОШИБКА СТОКА: RPC вернула «распродано», но в таблице …`
или `МАГАЗИН: ВНИМАНИЕ тираж не списан (stock_ready=false)`.


## 4.2. Тираж капсул: «Осталось: 1000 из 1000» не меняется

**Почему так было.** Продажа шла, а `UPDATE capsule_stock` падал (RLS или строки нет),
и ошибка глоталась: сервер считал, что списание прошло. Каталог при этом отдавал
полный тираж — отсюда «1000 из 1000» после покупки 30 капсул.

### 4.2.1. «Осталось: 1 000 из 1 000», а покупка → «Товар распродан»

**Симптом.** Карточка уверенно показывает полный тираж, а на «Купить» приходит
`400 Товар распродан`.

**Причина.** В `capsule_stock` **нет строки** для предмета (сид не применяли, строку
удалили, `INSERT` режет RLS). Каталог подставлял вместо остатка полный тираж —
`stock = total`, — а `shop_take_stock` строки не находил и возвращал `-1`
(«распродан»). Одно и то же отсутствие строки давало два противоположных сообщения.

**Лечение (одна команда, можно применять повторно):**
`supabase/migrations/20261106000000_stock_limits_on.sql` — создаёт таблицу, добивает
недостающие строки тиража (`ON CONFLICT DO NOTHING`: проданное не возвращается),
пересоздаёт `shop_take_stock` / `shop_return_stock` / `shop_stock_list`
с `SECURITY DEFINER`, выдаёт гранты и политику RLS и делает `NOTIFY pgrst`.

**Что изменилось в коде:**

- остаток считается известным только при наличии строки: `stock_ready=false`
  вместо фальшивого «1 000 из 1 000», в карточке — «Остаток уточняется»;
- на покупке `-1` от функции больше не означает «распродан» автоматически:
  сервер перечитывает таблицу, при отсутствии строки создаёт её и повторяет списание;
  «Товар распродан» отдаётся только когда в таблице действительно `0`;
- если списать так и не удалось (RLS/нет таблицы), покупка проходит, но ответ
  содержит `stock_ready=false` и `stock_warning`, а клиент перестаёт показывать
  число остатка до перезапуска аппки (иначе оно врёт);
- `/api/health` → `shop_stock.missing_rows` и `shop_stock.hint` называют, каких
  строк нет и какую миграцию применить; `!сервисы` в боте пишет то же самое.

**Что теперь.** Списание — одна атомарная SQL-функция `shop_take_stock` из миграции
`supabase/migrations/20261102000000_stock_and_chest_rpc.sql`:

```sql
UPDATE capsule_stock SET stock = stock - 1 WHERE item_id = … AND stock > 0 RETURNING stock;
```

Функция `SECURITY DEFINER`, поэтому работает даже когда RLS на таблице включён,
а сервис ходит ключом `anon` (service-role ключ не обязателен).

**Сигнатура функции (версия 20261103).** Сервер вызывает её так:

```python
supabase.rpc("shop_take_stock", {"p_item_id": "capsule", "p_amount": 1}).execute()
```

Функция объявлена как `shop_take_stock(p_item_id text, p_amount integer DEFAULT 1)`,
поэтому работают оба вызова — с `p_amount` и без него. Возвращает остаток после
списания (`0` — продан последний экземпляр), `-1` — распродан, `-2` — нет таблицы.
Код понимает и `boolean`-контракт (`True`/`False`), если функция написана так.

> Если вы применяли только `20261102000000_stock_and_chest_rpc.sql` (функция с одним
> параметром), PostgREST отвечал `PGRST202` на вызов с `p_amount`, и списание уходило
> в старый путь с `UPDATE`. Примените `supabase/migrations/20261103000000_shop_take_stock_amount.sql`
> и выполните `NOTIFY pgrst, 'reload schema';`.

**Как проверить, что транзакция прошла** — логи `aura-api` в Render, одна строка на
покупку:

```
СТОК capsule: rpc shop_take_stock{'p_item_id': 'capsule', 'p_amount': 1} → 999 ('ok')
МАГАЗИН: куплено user_id=… item=capsule баланс→9900 остаток→999 stock_ready=True
```

Когда тираж только что завели, в логе видно самолечение (строк не было — создали
и списали со второй попытки):

```
СТОК capsule: rpc shop_take_stock{'p_item_id': 'capsule', 'p_amount': 1} → -1 ('sold_out')
СТОК: созданы недостающие строки тиража ['capsule', 'uniq_capsule', …]
СТОК capsule: повтор {'p_item_id': 'capsule', 'p_amount': 1} → 999 ('ok')
```

А это — тот самый баг, если миграцию ещё не применили (покупка проходит, остаток
не ведётся):

```
ОШИБКА СТОКА: capsule нет строки в capsule_stock — примените …/20261106000000_stock_limits_on.sql
МАГАЗИН: ВНИМАНИЕ тираж не списан (stock_ready=false) item=capsule — …
```

Если функция недоступна, в логе будет `RPC shop_take_stock не найдена — списываем
условным UPDATE (старая схема)`, а при запрете записи — `ОШИБКА СТОКА: …`.

**Быстрая диагностика без логов:** откройте в браузере
`https://<сервис>/api/stock_debug` — там видно:

- `rpc_ready: true` — функция найдена и отвечает;
- `attempts[].params` — какая сигнатура сработала (`p_item_id` + `p_amount`);
- `attempts[].verdict: "sold_out"` на пробном id — правильный ответ (списывать нечего);
- `snapshot` — остаток, который сейчас видит магазин;
- `build` — версия кода; если в `/api/health` стоит старый `build`, значит Render ещё
  не задеплоил ветку `main`.

Пробный вызов безопасен: он идёт с несуществующим `item_id` (`__probe__`) и ничего
не списывает.

Если вместо этого видно:

```
ОШИБКА СТОКА: списание capsule через RPC: …
```
— значит функция не найдена/база отказала; покупка при этом не отменяется, но клиент
перестаёт показывать «Осталось: X из Y» (число скрывается, чтобы не врать), а
`!сервисы` пишет строку «🎟️ Тираж: ❌ …».

**Проверки без бота:**

1. `https://<сервис>/api/health` → блок `"shop_stock": {"ready": true, "left": {"capsule": 999, …}}`,
   а `missing_rows` должен быть пустым списком. Если там есть id — строк тиража нет,
   примените `20261106000000_stock_limits_on.sql`.
2. Supabase → Table editor → `capsule_stock`: `stock` уменьшается после каждой покупки.
3. Купить последнюю капсулу: карточка исчезает из магазина, повторная покупка
   отвечает `400: Товар распродан`.

**Уже проданное до фикса не списалось.** Если капсулы покупались, пока сток не
уменьшался, скорректируйте остаток один раз вручную (Supabase → SQL Editor):

```sql
-- пример: продано 30 обычных капсул «в никуда»
UPDATE public.capsule_stock SET stock = GREATEST(0, stock - 30), updated_at = now()
WHERE item_id = 'capsule';
```

**Если функции нет вообще** (миграции не применены) код падает обратно на условный
`UPDATE … WHERE stock = <прочитанный остаток>` и пишет
`СТОК capsule: списано 1, осталось 999 (без RPC)` — счётчик работает и так, но
атомарность гарантирует только SQL-функция. Когда RPC доступна, никакого `UPDATE`
таблицы не происходит: списание идёт одним вызовом функции (это проверяется тестом).

## 4.3. Апгрейд: стрелка и вердикт не расходятся

**Правило ровно одно, и оно одинаковое на сервере и на клиенте:**

| Бросок | Зона на круге | Итог |
|---|---|---|
| `roll < chance` | зелёная `0 → chance` | победа |
| `roll == chance` | сама граница (белая риска) | **победа** |
| `roll > chance` | красная `chance → 100` | проигрыш |

Стрелка и заливка считают угол **одной функцией** `upgradeAngleForPercent(%)`
(`% * 3.6`): `--p` круга, белая риска границы и позиция стрелки не могут разойтись.
У самой границы держится видимый зазор `0.6 п.п.` (2.16°): победа встаёт внутрь
зелёного, проигрыш — внутрь красного, поэтому «стрелка в красной зоне, а победа»
больше не встречается. Дальше зазора стрелка стоит ровно на броске.

Сервер (`api.py`, `upgrade_action`):

```python
chance_verdict = round(min(100.0, max(0.0, real_chance)), 2)   # ровно то, что уйдёт клиенту
roll = round(random.uniform(0.0, 100.0), 2)                    # 0.00..100.00
won = roll <= chance_verdict                                   # граница — победа
```

В ответе `chance` и `real_chance` — одно и то же число (`50.00`), лог `upgrade_log`
пишет его же, поэтому «сравнили с 47.5, а нарисовали 48» невозможно.

Клиент (`miniapp/app.js`):

- `upgradeRollWon(roll, chance)` → `roll <= chance` — та же граница;
- `upgradeArrowTargetFor` ставит стрелку на `roll * 3.6°`, но жёстко зажимает её в зону
  вердикта: при победе угол не может оказаться правее `chance`, при проигрыше — левее
  `chance`. Это односторонний зажим, а не «сдвиг только у самой границы», поэтому
  даже противоречивый ответ сервера не нарисует «стрелка в красном, а победа»;
- зазор у границы: `0.6 п.п.` (2.16°) внутри зелёного для победы и **пропорциональный**
  для проигрыша (`upgradeArrowRedClearanceDeg`). При шансе `99.99%` красная зона —
  всего `0.036°`, и фиксированный зазор вынес бы стрелку за 360°, то есть в ноль,
  обратно в зелёный. Теперь зазор не больше 60% красной зоны;
- `lockUpgradeChance()` фиксирует `--p` тем же числом, что пришло с сервера, ещё до
  остановки стрелки — зона и вердикт всегда про одно число;
- после остановки `finishUpgradeAnimation()` ещё раз доводит стрелку тем же расчётом:
  если анимацию прервали (повторный клик, уход с экрана), итоговый кадр всё равно
  показывает зону вердикта;
- белая риска внутри круга удалена (задача 26), стрелка вынесена наружу — см. §4.3.1.1;
- заливка круга теперь ставится **из JS** (`upgradeRingGradientCss()` →
  `conic-gradient(from 0deg, …)`) тем же углом `% * 3.6`, поэтому даже устаревший
  `style.css` из кэша Telegram не может повернуть круг на 90° и «перекрасить»
  вердикт; в `index.html` добавлены `Cache-Control/Pragma/Expires` мета-теги;
- зелёная зона: `conic-gradient(from 0deg, #22c55e 0 var(--p), #ef4444 var(--p) 360deg)`.

> **Почему именно `from 0deg`.** В CSS у `conic-gradient` ноль — это 12 часов, то есть
> ровно тот же ноль, от которого считается стрелка (`rotate(0deg)` → вверх). Раньше в
> стилях стояло `from -90deg`: круг был повёрнут на 90°, и при шансе 50 % зелёным
> оказывался ВЕРХ круга вместо ПРАВОЙ половины. Из-за этого победа с броском 30 %
> рисовалась в красной зоне («на красном зашло»), а проигрыш с броском 80 % — в
> зелёной («на зелёном не может»). Вердикт при этом был правильный — врал именно
> визуал. Тест `test_upgrade_geometry.js` проверяет, что ноль заливки, риски и
> стрелки совпадает, и что цвет под стрелкой всегда равен вердикту.

**Если «стрелка в красной зоне, а засчитали победу»:** почти всегда это старый
`app.js` в кэше Telegram. С версии `?v=aura-9` сервер отдаёт `index.html` с
`Cache-Control: no-cache`, а скрипты кэшируются по номеру версии — при следующем
открытии аппки клиент получает актуальный код. Проверить логику без браузера:
`POST /api/upgrade_action` (админ) — в ответе `roll`, `real_chance`, `won` должны
удовлетворять `won == (roll <= real_chance)`.

## 4.3.1. Шансы апгрейда: `шанс = 90 / X`

**Задача 27.** Фиксированная таблица 78/65/55/50 убрана: она противоречила подписи
под кругом («Шанс = стоимость вашего предмета / стоимость цели») — при x1.75 игрок
видел 50 %, хотя честный расчёт 1000/1750 даёт 57 %. Теперь шанс считается одной
формулой и на сервере, и на клиенте:

```python
api.py:          UPGRADE_CHANCE_NUMERATOR = 90.0
                 chance = 90 / множитель
miniapp/app.js:  UPGRADE_CHANCE_NUMERATOR = 90
```

Формула действует для **любого** X в диапазоне `1.12 … 50`, в том числе для числа,
выбранного ползунком:

| Множитель X | Шанс 90/X | Честный 100/X | Выплата при победе |
|---|---|---|---|
| x1.12 | 80.36 % | 89.3 % | ставка × 1.12 |
| x1.35 | 66.67 % | 74.1 % | ставка × 1.35 |
| x1.55 | 58.06 % | 64.5 % | ставка × 1.55 |
| x1.75 | 51.43 % | 57.1 % | ставка × 1.75 |
| x20 | 4.50 % | 5.0 % | ставка × 20 |
| x50 | 1.80 % | 2.0 % | ставка × 50 |
| x4 (свой) | 22.50 % | 25.0 % | ставка × 4 |
| x8 (свой) | 11.25 % | 12.5 % | ставка × 8 |
| x12.5 (свой) | 7.20 % | 8.0 % | ставка × 12.5 |

Числитель 90 (а не 100) — это и есть встроенный дом-эдж 10 %: игрок видит ровно то,
по чему играет, а не «почти честные» проценты.

Правила, которые нельзя нарушать:

- **что нарисовано, то и играется**: сервер отдаёт `chance`, клиент рисует это же
  число (зелёная зона `0 → chance`, стрелка на `roll * 3.6°`), победа — `roll <= chance`;
- диапазон множителя зашит на сервере: `UPGRADE_MIN_MULTIPLIER = 1.12`,
  `UPGRADE_MAX_MULTIPLIER = 50.0`. `1.0`, `1.11`, `50.5`, `100` → HTTP 400
  «Множитель должен быть от x1.12 до x50», а не «Слишком большой апгрейд»;
  `4`, `8`, `12.5`, `49.99` — валидны;
- дом-эдж больше **не зависит от баланса**: `upgrade_house_edge` по умолчанию `1.0`.
  Если админ поставит другое значение в `/admin` (0.8 / 1.0 / 1.2), оно применится
  симметрично к игре и к кругу (`/api/user → economy.upgrade.house_edge`);
- `upgrade_chance_factor` (админский множитель) приходит с сервера и применяется
  так же симметрично; не-админам шанс делится на 2;
- для цели «по проценту» и для капсул шанс по-прежнему считается как
  `стоимость слева / стоимость цели`;
- `/api/user → economy.upgrade` отдаёт `chance_numerator`, `mult_min`, `mult_max` и
  посчитанный `multiplier_chances` — клиент не хранит своих копий чисел.

Проверка: `/admin → 🎲 Шансы` показывает формулу «шанс = 90 / X» и пример x1.75 →
`51.43 %` (строки «Меняется без деплоя…» там больше нет). В Mini App на плитке
x1.75 должно быть ровно `51.43%`, у x50 — `1.80%`. Если числа другие, на сервисе
старый `app.js`/`api.py` (сейчас статика подключается как `?v=aura-30`).

капсулы приглушены, но видны. Целью тоже может быть любая капсула.

## 4.3.1.3. Арена: обычная с мячиком и командная

Задача 26 вернула **поле с мячиком** для обычной арены и оставила переключатель:

| Режим | Что видно | Как решается победитель |
|---|---|---|
| **Обычная арена** | поле с вертикальными полосами (по доле ставки), аватарки и мяч | мяч летит по траектории сервера `/api/hockey_roll/{round_id}`, победитель — полоса под `final_x` |
| **Командная арена** | круг, два сектора (красные/синие), указатель | сектор по `final_x`, банк делится между игроками победившей команды пропорционально ставкам |

Клиент только рисует точки траектории (позиция считается по `rolling_started_at`),
поэтому результат не зависит от телефона и не может быть «подкручен» на клиенте.
Ботов и выплаты считает сервер (`_finish_hockey_round` / `_payout_hockey_winner`).

**Задача 27 — «вернуть как раньше», но живее:**

- **в обычной арене нет кнопок «за красных / за синих»** — `#arena-team-buttons`
  скрывается (`hidden` + `display:none` + `aria-hidden`), режим остаётся `normal`;
  в командной кнопки на месте, но синяя блокируется, когда вы уже за красных;
- **камера следит за мячом**: `#hockey-camera` → `#hockey-scene`, зум
  `1.32 → 1.55` по ходу раунда (`ARENA_CAMERA_ZOOM` / `ARENA_CAMERA_FINISH`),
  сдвиг `translate3d(-(x-0.5)·W·zoom, -(y-0.5)·H·zoom, 0) scale(zoom)`; после
  финиша (`settled`) отъезд до `1.12` за 700 мс, новый раунд — полный сброс;
- **анимации**: `arenaBallPulse` (мяч «дышит»), `arenaBallHalo` (световое пятно),
  `arenaSectorWin`/`arenaPieWin` (вспышка выигравшей полосы и команды),
  `arenaSectorIn` (плавное появление полос), `arenaBreath` и `arenaRingSpin`
  (фон и кольцо), `arenaChipIn` (появление аватарок в круге);
- **яркие цвета**: полосы рисуются градиентом `${tint}cc → 55` вместо прозрачных
  `22`-оттенков, поле — насыщенные радиальные градиенты на `#0f0f0f`.

**Задача 29 — обычная арена снова ровно как до командной:**

- полосы рисуются **внутрь сцены** (`#hockey-scene`), поэтому приближение камеры
  действует и на них; в полосах — только круглая аватарка/буква по центру
  (`.player-shape`), без подписей и процентов; ширина = доля ставки, последняя
  полоса добирает остаток до 100 %;
- камера: `applyHockeyCamera(x, y, elapsed)` ставит `transform-origin` в точку
  мяча и масштабирует поле `1 → 1.55` по smoothstep с 4.5-й секунды
  (`ARENA_CAMERA_ZOOM_START` / `ARENA_CAMERA_MAX_ZOOM`), поэтому мяч остаётся на
  месте, а поле «наезжает» на него; после финиша камера остаётся на победителе,
  новый раунд — `scale(1)`;
- мяч идёт по траектории сервера шагом 0.05 с (`HOCKEY_SIMULATION_STEP`) от
  серверного `rolling_started_at` через `performance.now() + hockeyServerOffsetMs`
  — открыл экран в середине раунда, мяч уже там, где надо;
- вернулся **звук отскока** (`playSound('thud')`, не чаще 140 мс);
- **дёрганье иконок и «нет анимаций»**: обе арены перерисовывались целиком каждые
  200 мс опроса, и каждая новая нода заново запускала CSS-анимацию появления.
  Теперь у поля и у круга есть «подпись» состояния (`arenaSignature`: id, ставка,
  цвет, команда, аватар), и DOM не трогается, если ничего не изменилось;
  список участников обновляется по `data-signature`.

**Командная арена — стрелка реально крутится и выбирает победителя.**
Было: `arenaPointer.roundId` записывался ещё на статусе «Ставки», поэтому на
броске проверка «раунд сменился» уже не срабатывала и стрелка стояла на нуле.
Теперь `arenaStartPointerSpin()` крутит её через `requestAnimationFrame`
(520°/с) всё время броска, а на финише `arenaLandPointer(final_x, 1300)`
плавно тормозит ровно на выигрышном секторе (`cubic-bezier(0.12,0.72,0.12,1)`),
подсвечивая наконечник золотом (`.arena-pointer.landing`). Опрос состояния
вращение не сбивает: спин запускается один раз и живёт в своём rAF.

Важно: `display:inline-flex` перебивает атрибут `hidden`, поэтому в `style.css`
есть жёсткое правило `.love-badge[hidden], .sub-banner[hidden],
.hockey-arena[hidden], .arena-team-buttons[hidden] { display: none !important }`.
Без него одновременно висели обе плашки профиля и баннер подписки.

**Задача 31 — две арены одновременно, переключение в любой момент.**
Раньше режим арены был один на сервер и менялся только между раундами
(`POST /api/arena_mode` отвечал «Режим переключим после этого раунда»), а
`place_bet` искал игрока только по `id` и запрещал красных вместе с синими —
поэтому «посмотреть вторую арену, пока идёт катка» было невозможно.

- **Два независимых котла в одном раунде.** У каждого игрока в записи есть поле
  `arena` (`normal` / `team`); `_arena_players(arena)` / `_arena_bank(arena)`
  отдают участников и банк конкретного котла, `game_state["bank"]` — их сумма.
  Проценты (`percent`) считаются внутри своего котла.
- **Одна траектория — два победителя.** `final_x` по-прежнему одна на раунд,
  но `_finish_hockey_round` разрешает по ней **оба** котла:
  `game_state["arena_winners"] = {"normal": …, "team": …}`, а
  `_hockey_payout_plan()` собирает общий план выплат (в записи есть `arena`).
  Деньги котлов не смешиваются: в обычной победитель забирает банк своего котла,
  в командной банк делят игроки победившей команды пропорционально ставкам.
- **Ставки в обе арены.** `POST /api/place_bet` принимает `arena`
  (`normal` | `team`); без `arena` работает старый контракт (`team` → командная).
  Запись уникальна в пределах котла, лимит `MAX_BET = 10 000` считается **на
  каждую арену отдельно**, запрет «красные + синие» остался только внутри
  командной арены. `POST /api/arena_mode` больше ничего не блокирует (no-op,
  отвечает `mode: "both"`).
- **Состояние сразу для двух арен.** `GET /api/hockey_state` отдаёт
  `arenas: {normal: {players, sectors, bank, winner, …}, team: {players, sectors,
  teams, bank, winner, winner_team, …}}` плюс плоские поля (`normal_players`,
  `team_players`, `normal_bank`, `team_bank`, `sectors`, `team_sectors`) для
  старого клиента.
- **Клиент переключается локально.** `setArenaMode(view)` не делает запросов:
  пишет `arenaState.view`, перерисовывает поле/круг, банк и список участников из
  уже полученного снимка (`syncArenaView`). Переключатель работает в `waiting`,
  `rolling` и `finished`; при возврате на арену её анимация (мяч/стрелка)
  проигрывается заново по текущему состоянию (`replayArenaAnimation`).
- **Боты в обеих аренах.** `_maybe_add_hockey_bots` наполняет оба котла за один
  тик (раньше `break` после первой арены оставлял командную пустой), команды
  командной арены держатся примерно равными, кит приходит в тот котёл, где была
  крупная ставка (`whale_arena`).

## 4.3.1.4. Отношения: «свободен» и `топ отношений`

- Профиль Mini App: показывается **ровно одна** плашка. Если пары нет — зелёная
  «💚 Свободен/Свободна» (род по имени: Анна → Свободна, Данил → Свободен) и
  **ничего больше**: подсказки «+любовь @ник в боте» и упоминания команды там нет
  (задача 27). Если пара есть — розовая «💛 В отношениях с @ник» с этапом и Love
  коинами, а зелёная скрыта. Обе плашки взаимоисключающие — см. правило
  `[hidden] → display:none !important` в §4.3.1.3.
- **Этапы и награды за них — секретная механика (задача 29).** Ни в одной
  публичной команде нет названий этапов, сумм наград и «следующего этапа»:
  `топ отношений` показывает только пары, Love и сколько они вместе; РП-действие
  пишет «💞 Ваша пара стала ещё ближе» и не объявляет приз; предложение отношений
  не обещает выплат; `/api/love_state` отдаёт `level`, `stage.title`, `love`,
  `progress` и **не** отдаёт `reward`, `next_stage` и `stage_rewards` (только флаг
  `stage_up`). Награда при этом начисляется как раньше — просто тихо.
- `все рп` (или `рп команды`, `список рп`) — полный список РП-команд: 29 действий
  с эмодзи и описанием. Набор расширен: `поцеловать в щёку`, `поцеловать в лоб`,
  `чмокнуть`, `обнять крепко`, `приобнять`, `погладить по волосам`, `щекотать`,
  `подмигнуть`, `укутать`, `носить на руках`, `сделать массаж`,
  `шептать на ушко`, `подарить цветы`, `спеть серенаду`, `дать пять`,
  `чокнуться`, `смотреть фильм`, `гулять под луной`, `танцевать вальс` и старые.
- `отн инфа` (или `отн инфо`, `инфа отношений`) — карточка пары: **с кем**
  (ник), **сколько дней вместе**, **уровень** и **Love коины**. Смотреть можно
  только свои отношения: на просьбу про другого игрока бот отвечает «Отношения —
  личное» и советует, чтобы тот написал сам. **Исключение — админы**
  (`ADMIN_IDS`): им доступна карточка любого игрока (ответом на сообщение или
  `отн инфа @ник`).
- `+любовь @ник` в **любом чате**, если у цели уже есть пара, отвечает с ником
  партнёра: «💔 @nick уже состоит(ит) в отношениях с @partner». То же при нажатии
  «Да» на устаревшее предложение.
- Бот: `топ отношений` (или `топ любви`) — сводка пар и Love (без этапов) и
  топ-10 пар по Love. Отношения лежат в Supabase (`relationships`) и **общие для всех
  чатов**: пара, созданная в одном чате, видна в другом.
- Второй роман невозможен: бот проверяет обе стороны при «Да», а миграция
  `20261118000000_love_guard_and_upgrade_chances.sql` ставит триггер
  `love_single_active_relationship_trg`, который не даст создать вторую активную
  пару даже при одновременном нажатии.

## 4.3.1.5. Свой множитель: ползунок 1.12 … 50

Задача 27: X можно не только выбирать плитками, но и **крутить ползунком** от
минималки до максималки.

- элемент `#up-custom-range` (`min="0" max="1000"`), рядом `#up-custom-value`
  («x3.70») и `#up-custom-chance` («24.32 %»);
- шкала **логарифмическая**: позиция 0 → x1.12, 1000 → x50 (`upgradeMultFromSlider`),
  иначе низкие множители занимали бы пиксель. Обратное преобразование —
  `upgradeSliderFromMult`, поэтому ползунок и плитки не рассинхронизируются;
- `oninput` пересчитывает число, шанс и потенциальный выигрыш живьём,
  `onchange` фиксирует выбор (и на тач-устройствах, где `input` идёт редко);
- серверу уходит `multiplier` — любое значение в диапазоне (шаг 0.01), отдельный
  список пресетов больше не нужен;
- `miniapp/style.css`: `.up-custom-*` — тёмная тема `#1c1c1c`, акцент `#00e676`.

## 4.3.1.6. Апгрейд: ставка списывается сразу после нажатия

Сервер списывал ставку **до** броска и всегда (`upgrade_action`: баланс/капсулы
уменьшаются перед `secrets`-броском, `won = roll <= chance`), но клиент показывал
старый баланс все 3.4 секунды анимации — со стороны это выглядело так, будто
деньги не списались.

Теперь клиент делает **оптимистичное списание сразу**:

- `applyUpgradeStakePreview()` уменьшает баланс (или количество капсул) и
  вызывает `updateUI()` ещё до ответа сервера — при нажатии «АПГРЕЙД» деньги
  уходят с экрана мгновенно;
- форма апгрейда на время раунда заморожена (`ensureUpgradeSourceValid` выходит
  при `upgradeBusy`), иначе при ставке «все капсулы» источник перескочил бы на
  коины и подпись «Выигрыш» разошлась бы с реальной ставкой;
- если сервер отказал (нет денег, лимиты, сеть) — `restoreUpgradeStakePreview()`
  возвращает ставку на место и баланс подтверждается через `loadUserData()`;
- приз приходит в конце анимации: `applyUpgradeServerState(data)` берёт только
  серверный `new_balance`/`new_inventory`, поэтому итог всегда равен базе.

Проверка: поставить коины и нажать «АПГРЕЙД» — баланс в шапке и в плашке игры
уменьшается **сразу**, а не после остановки стрелки; при проигрыше он остаётся
уменьшенным, при победе — увеличивается на выплату в конце прокрутки.

## 4.3.1.6.1. Задача 32: рефка, пассивка и плитки команд

**Реферальная ссылка больше не ведёт на чужого бота.** Mini App подставлял в
ссылку `initDataUnsafe.bot_username`, то есть имя того бота, из которого
открыли страницу — у проекта есть старый бот, и игроки получали
`https://t.me/Auragameplay_bot?startapp=ref_…`. Теперь имя бота определяет
сервер: `BOT_USERNAME` (env) → Telegram `getMe` по `BOT_TOKEN` → константа
`AuragameBot`, а `/api/referrals` отдаёт готовую ссылку
`https://t.me/AuragameBot?startapp=ref_<id>` вместе с `bot_username`.
Клиент шаблон `{bot}` больше не подставляет сам. Если на `aura-api` задан
`BOT_TOKEN` бота, имя подтянется само даже после переименования.

**Пассивный доход копится всегда.** Раньше подсказка честно говорила
«начисление идёт, пока аппка открыта» — и это был реальный потолок. Сейчас
доход считает сервер по `last_at`, поэтому он капает и при закрытой аппке, а
игрок забирает накопленное при следующем заходе:

- `GET /api/user` и `/api/health` отдают `passive_night`
  (`{multiplier: 0.5, from: 22, to: 8}`);
- **ночь по МСК (22:00–08:00) — вдвое дешевле.** Интервал режется по границам
  `22:00`/`08:00`, поэтому «21:00–23:00» даёт 1 час полной ставки и 1 час
  половинной (`_passive_split_hours`);
- за один заход считаем не больше 24 часов (`PASSIVE_INCOME_MAX_HOURS`), но
  **накопленное не сгорает**: отметка сдвигается только на оплаченные часы,
  и следующий заход добирает остаток — неделя отсутствия забирается за 7
  заходов подряд;
- ответ `POST /api/passive_income` дополнен `real_hours`, `night`,
  `night_multiplier`, `night_window`;
- если таблицы `passive_income` нет — всё равно работает (`degraded: true`,
  отметка в памяти процесса).

**Разрыв отношений — `-отны`.** Основная команда теперь `-отны` (`-отны аура`
тоже подходит), старые `-отн`, `-отношения`, `-пара`, `-любовь` и `разлюбить`
продолжают работать. В справке `!помощь` и во всех подсказках бота — новая форма.

**Командная арена: участники по двум плиткам.** Внизу больше нет одной ленты:
слева плитка 🔵 синих, справа плитка 🔴 красных (`#arena-team-boards`,
`renderTeamBoards` в `app.js`). В каждой плитке — состав команды, отсортированный
по ставке, сумма банка команды, своя ставка подсвечена, победившая команда
получает золотую рамку. В обычной арене остаётся прежняя лента участников.

## 4.3.1.6.2. Задача 33: «Не удалось создать пару», бонус за канал, Stars и арена

**Пара не создавалась («примените миграцию»).** Причин было три, и все три
лечатся одной миграцией `supabase/migrations/20261124000000_love_fix.sql`:

- таблицы `relationships` нет (не применялась `20261109000000_economy_social.sql`);
- таблица есть, но без колонок `bank` / `status` / `created_at` / `updated_at`
  (`PGRST204: Could not find the 'bank' column`);
- RLS включён, политики нет → `new row violates row-level security policy`.

Помимо SQL это исправлено и в коде:

- `bot.py → _create_relationship()`: если база ругается на отсутствующую
  «украшающую» колонку (`bank`, `status`, `love`, `updated_at`), вставка
  повторяется без неё — пара создаётся даже на старой схеме;
- `bot.py → _relationship_failure_message()`: вместо бесполезного «примените
  миграцию» игрок видит настоящую причину — RLS, отсутствие таблицы/колонки
  (с её именем) или «кто-то уже в паре, сначала `-отны`».

**Бонус за канал больше не зависит от проверки.** `getChatMember` часто
недоступен (бот не админ канала, канал закрыт, Telegram не ответил), и игроки
вообще не получали 200 коинов. Теперь:

- бонус выдаётся один раз за всё время (`subscriptions_history`), даже если
  проверка не удалась (`check_skipped: true` в ответе);
- в личку бота приходит подтверждение: «Бонус за подписку получен! +200,
  баланс…, задание выполнено — в приложении оно больше не появится»;
- при следующем заходе плашка задания скрыта (`bonus_claimed`);
- вернуть строгую проверку: `CHANNEL_BONUS_STRICT=1` в переменных `aura-api`.

**Покупка коинов за Stars — «Скоро…».** В профиле карточка размыта
(`.profile-extra.is-soon`) с оверлеем «Скоро…», кнопка карточки подписана так же,
а «+» у баланса отвечает тем же текстом и не открывает пустую модалку. Пакеты
даже не запрашиваются. Включить обратно — `let STARS_SOON = false` в `app.js`
(серверный флаг `STARS_ENABLED` остаётся).

**Арена: анимации как всегда.** Серая подсказка «Две арены идут параллельно…»
удалена. Переключение арен больше не перезапускает анимации:

- мяч не начинает траекторию заново — он продолжает с текущей точки по
  серверному времени (`arenaBall.roundId` не сбрасывается, добавлено условие
  `!arenaBall.active`);
- стрелка при возврате на командную арену уже разыгранного раунда ставится
  на победителя мгновенно (`arenaPointerJumpTo`), без второго «доезда» на 3.2 с;
- новый раунд по-прежнему сбрасывает и мяч, и стрелку в исходное положение.

## 4.3.1.7. Одиночки (Unlove) и `-отны` (старое `-отн`) — задача 30

**Зачем.** Раньше без пары игрок ничего не получал: `поцеловать` отвечало
«сначала предложи отношения», и половина чата не могла качать Love вообще.

**Как теперь:**

- **Одиночный счёт `Unlove`.** У кого пары нет — тот пишет любую РП-команду
  (`обнять`, `поцеловать`, `подарить цветы`…) и получает ровно те же
  `+10`, тот же кулдаун 5 часов и те же этапы, что и пара. Разница одна:
  награду за этап получает **один человек**, а не двое. Валюта хранится в
  `solo_love` (одна строка на игрока), оплаченные этапы — в
  `solo_love_stage_rewards` (PK `user_id, stage`, повтор невозможен).
- **Передать Love/Unlove другому нельзя.** Ни команды, ни кнопки для этого
  нет: если одиночка пишет `поцеловать @ник`, ник получает только фразу в
  чате, а `+10` уходит автору. Награда всегда зарабатывается сама.
- **Вступление в отношения сжигает одиночный счёт.** `solo_love` удаляется у
  обоих, история начинается с `Love = 0`. Оплаченные одиночные этапы
  остаются закрытыми — иначе награды фармились бы по кругу
  «пара → развод → снова один».
- **`отн инфа` для одиночки** показывает уровень и `Unlove` вместо пары;
  чужие отношения по-прежнему видит только админ (`ADMIN_IDS`).
- **`топ отношений` — только пары.** Одиночки в статистику не попадают
  вообще, даже с огромным `Unlove`.
- **`-отны` (алиасы `-отн`, `-отношения`, `-пара`, `-любовь`, `разлюбить`)**
  **удаляет строку пары**, а не помечает её `broken`: у обоих исчезает
  статус и весь накопленный Love. Уже выплаченные награды не отзываются —
  деньги никто не отбирает.

**Профиль Mini App:** зелёная плашка «💚 Свободен/Свободна» дополняется
`· ур. N · M Unlove` (только когда счёт больше нуля) — данные берёт
`/api/love_state` (`solo`, `unlove`, `solo_level`, `solo_title`, `solo_days`).

**SQL:** `supabase/migrations/20261122000000_solo_love.sql` — он же заново
создаёт `passive_income`, если её не было (§4.3.1.8).

## 4.6. aura-api падает на старте: `ModuleNotFoundError: No module named 'aiohttp'`

**Симптом.** В логах Render: build successful, затем

```
==> Running 'uvicorn api:app --host 0.0.0.0 --port $PORT'
ModuleNotFoundError: No module named 'aiohttp'
```

(в логе build видно `Running build command 'pip install fastapi uvicorn supabase
python-dotenv'` — значит, сервис собирается **не** по `requirements.txt`).

**Причина.** `api.py` импортировал `aiohttp` на верхнем уровне, а в этой сборке
его нет: `aiohttp` ставится только из `requirements.txt`, который Render в
данном случае не читает.

**Что уже сделано (код).** `api.py` больше не требует `aiohttp`: клиент для
Telegram выбирается в рантайме — `httpx` (приходит вместе с `supabase`) →
`aiohttp` (если установлен) → стандартный `urllib`. Проверить, что попало на
сборку:

```bash
curl -s https://aura-api-mptt.onrender.com/api/health | grep -o '"http_client":"[a-z]*"'
```

`"http_client":"httpx"` — всё в порядке. `"urllib"` — нет ни `httpx`, ни
`aiohttp`: тогда точно поправьте Build Command (ниже).

**Что лучше поправить в Render (Dashboard → aura-api → Settings → Build &
Deploy).** Поставить Build Command:

```
pip install -r requirements.txt
```

и нажать **Manual Deploy → Clear build cache & deploy**. Тогда сервис получает
весь список целиком, включая `fastapi`, `uvicorn`, `supabase`, `python-dotenv`,
`aiohttp`. `requirements.txt` лежит в корне репозитория и подходит для обоих
сервисов.

**Правило на будущее.** Любую библиотеку, которую использует `api.py`, нужно
либо импортировать «мягко» (как теперь `httpx`/`aiohttp`), либо держать в
Build Command сервиса: при сборке без `requirements.txt` ломается не сборка, а
именно старт процесса, и Render показывает только «Application failed to
respond» / бесконечный деплой.

## 4.7. «Application exited early»: команды Build и Start перепутаны

**Симптом.** Деплой доходит до конца, потом в логе:

```
==> Deploying...
==> Running 'pip install -r requirements.txt'
Successfully installed ...
==> Application exited early
==> Instance srv-... restarted
```

**Причина.** `pip install -r requirements.txt` стоит в поле **Start Command**.
Render запускает эту команду как процесс сервиса: пакеты ставятся, `pip`
завершается с кодом 0 — Render видит «приложение вышло само» и перезапускает.

**Как должно быть (два разных поля):**

| Сервис | Build Command | Start Command |
|---|---|---|
| `aura-api` | `pip install -r requirements.txt` | `uvicorn api:app --host 0.0.0.0 --port $PORT` |
| `dan4Bot` | `pip install -r requirements.txt` | `python bot.py` |

Render Dashboard → сервис → **Settings → Build & Deploy**:

- **Build Command** — установка зависимостей, выполняется один раз при сборке;
- **Start Command** — долгоживущий процесс; он НЕ должен завершаться сам.

После исправления: **Manual Deploy → Clear build cache & deploy**. В логе
должно быть `==> Running 'python bot.py'`, затем строки бота:

```
🤖 Бот: @... | Mini App: https://aura-api-mptt.onrender.com/miniapp/
🔗 Прямая ссылка Mini App: ...
```

Признак правильного старта `dan4Bot`: сервис не перезапускается, `/health`
этого сервиса отвечает `OK` (бот поднимает минимальный HTTP-сервер
`start_fake_website`, потому что Render убивает Web Service без открытого порта).

**Если Start Command верный, а процесс всё равно падает:**

- `raise SystemExit("❌ ОШИБКА: Не найден BOT_TOKEN!")` — не задана переменная
  `BOT_TOKEN` (Environment → Add Environment Variable).
- `TelegramUnauthorizedError` — токен отозван/перепутан (BotFather → API Token).
- `get_me` больше не роняет старт с первого сетевого сбоя: в `bot.py` есть
  `get_me_with_retry()` (8 попыток с нарастающей паузой); неверный токен при
  этом по-прежнему падает сразу, без ожидания.

### 4.5.4. Все финансовые операции — только на сервере

Клиент не считает ни шансы, ни награды: он присылает намерение
(`amount`, `target_multiplier`, `request_id`) и рисует то, что вернул сервер.
Списание/начисление идёт в одной транзакции, а `idempotency_keys` защищает от
двойного клика и повторной доставки запроса. RNG — `secrets`, не
`random`/`Math.random`.

## 4.8. Задача 26: что применить в Supabase (один файл)

Файл `supabase/migrations/20261118000000_love_guard_and_upgrade_chances.sql` —
идемпотентный. Supabase → SQL Editor → New query → вставить целиком → **Run**.
Если миграция задачи 25 (`20261109000000_economy_social.sql`) ещё не применена —
сначала её, иначе таблиц `relationships`, `game_settings` не будет.

Полный текст (можно копировать прямо отсюда):

```sql
-- 1. Один активный роман на игрока (защита от гонки двух «Да»)
CREATE OR REPLACE FUNCTION public.love_single_active_relationship()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF NEW.status = 'active' THEN
        IF EXISTS (
            SELECT 1 FROM public.relationships AS r
            WHERE r.status = 'active'
              AND r.id IS DISTINCT FROM NEW.id
              AND (r.user_a IN (NEW.user_a, NEW.user_b)
                   OR r.user_b IN (NEW.user_a, NEW.user_b))
        ) THEN
            RAISE EXCEPTION 'Участник уже состоит в активных отношениях';
        END IF;
    END IF;
    RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS love_single_active_relationship_trg ON public.relationships;
CREATE TRIGGER love_single_active_relationship_trg
    BEFORE INSERT OR UPDATE OF user_a, user_b, status ON public.relationships
    FOR EACH ROW EXECUTE FUNCTION public.love_single_active_relationship();

CREATE INDEX IF NOT EXISTS relationships_status_idx ON public.relationships (status);
CREATE INDEX IF NOT EXISTS relationships_active_users_idx
    ON public.relationships (user_a, user_b) WHERE status = 'active';

-- 2. Шанс апгрейда: дом-эдж больше не 0.8 (иначе x1.75 показывал 40%)
INSERT INTO public.game_settings (key, value) VALUES ('upgrade_house_edge', '1.0')
ON CONFLICT (key) DO NOTHING;

UPDATE public.game_settings SET value = '1.0', updated_at = now()
 WHERE key = 'upgrade_house_edge' AND value = '0.8';

NOTIFY pgrst, 'reload schema';
```

Что это меняет:

- **второй роман физически невозможен** — вторая активная пара с тем же игроком не
  создастся, даже если двое нажмут «Да» одновременно;
- **x1.75 = 51.43 %** (а не 45.71 %): шанс считается как `90 / X` (задача 27),
  дом-эдж по умолчанию выключен (`1.0`) и, если его поменять в `/admin`, клиент
  получит новое значение через `/api/user` — круг и вердикт останутся одним числом.

Без этой миграции: игра и апгрейд работают (шансы читаются из кода), но защита от
второй пары останется только на уровне бота, а в `game_settings` будет висеть
старое `0.8` → круг покажет 40 % вместо 50 %.

## 4.9. «В базе не хватает колонки «created_at»» — что это значит и как чинить

**Задача 28.** Игрок видел алерт «В базе не хватает колонки «created_at» в
таблице users», хотя все миграции были применены. Причин две, и обе устранены.

### 4.9.1. Ошибка называла не ту таблицу

`api._db_error_detail()` всегда писала «в таблице **users**», потому что имя
таблицы было зашито в текст. PostgREST же говорит другое:

```
Could not find the 'created_at' column of 'subscriptions_history' in the schema cache
```

Теперь таблица и колонка **вытаскиваются из ответа базы** (`_sql_error_column_table`),
и текст выглядит так:

> В базе не хватает колонки «created_at» в таблице «subscriptions_history».
> Примените supabase/migrations/20261028000000_created_at_and_crash_history.sql.
> Если миграция уже применена — обновите кэш схемы: SQL Editor →
> `NOTIFY pgrst, 'reload schema';` (Dashboard → Settings → API → Reload schema).
> Данные игрока не потеряны.

То есть «применил же» больше не превращается в тупик: видно, **что именно**
не применено и что кэш PostgREST тоже надо обновить.

### 4.9.2. Отсутствие created_at больше не ломает игру

- запись в `subscriptions_history`, `referrals`, `stars_payments`,
  `idempotency_keys` идёт через `_insert_tolerant`: если база ругается ровно на
  `created_at`, строка пишется **без неё**, а в лог уходит предупреждение.
  Бонус за подписку, реферал и платёж Stars проходят;
- профиль (`/api/user`) при отсутствии `users.created_at` открывается, просто
  без «дней в игре». Повторные попытки backfill-а кэшируются
  (`_USERS_CREATED_AT_READY`), чтобы не забивать лог PGRST204 на каждый запрос;
- `created_at` считается **необязательной** колонкой в аудите: она помечается
  `•`, а не `❗` — играть можно.

### 4.9.3. Одна команда-диагностика

| Где | Как | Что показывает |
|---|---|---|
| Бот | `бд` (или `!бд`, `база`, `миграции`) — только админ, только в ЛС | нет таблиц / нет колонок (`users.created_at`), готовый SQL |
| API | `POST /api/db_audit` с `initData` админа | JSON: `missing_tables`, `missing_columns` (с флагом `optional`), `blocking`, `users_created_at`, `sql` |
| Health | `GET /api/health` → `db_audit` | ссылка на эндпоинт и подсказка про `бд` |

Список «что должно быть в базе» живёт в одном месте — `db_schema.py`
(`REQUIRED`, `COLUMN_TYPES`, `OPTIONAL_COLUMNS`). Его используют и API, и бот,
поэтому они не могут разойтись.

Пример ответа, когда колонки нет:

```json
{
  "ok": false,
  "users_created_at": false,
  "missing_columns": [{"table": "users", "column": "created_at", "optional": true}],
  "blocking": [],
  "sql": "ALTER TABLE public.users ADD COLUMN IF NOT EXISTS created_at TIMESTAMPTZ NOT NULL DEFAULT now();\n\nNOTIFY pgrst, 'reload schema';"
}
```

### 4.9.4. Миграция «добить всё разом»

`supabase/migrations/20261120000000_schema_audit_missing_columns.sql` —
идемпотентная: `ADD COLUMN IF NOT EXISTS` для `created_at` во всех таблицах,
где он нужен (`users`, `subscriptions_history`, `referrals`, `stars_payments`,
`idempotency_keys`, `shop_purchases`, `crash_history`, `upgrade_log`,
`relationships`), плюс `paid_at`, `updated_at`, `ice`, `premium`, `inventory`,
`last_chest`, `keys`, политики RLS «всё разрешено серверу» и
`NOTIFY pgrst, 'reload schema'` в конце.

Порядок действий, если алерт всё-таки появился:

1. написать боту `бд` (или дёрнуть `/api/db_audit` админом) — увидеть точный
   список `таблица.колонка`;
2. выполнить предложенный SQL (или миграцию `20261120000000_…`) целиком в
   SQL Editor;
3. последняя строка миграции делает `NOTIFY pgrst, 'reload schema'` — без неё
   PostgREST продолжит отдавать PGRST204 на новые колонки;
4. открыть Mini App заново и нажать «Подписаться на канал» — бонус 200 коинов
   начислится (он одноразовый, повторно не придёт).

Если в отчёте есть `❗`-строки — это блокирующие колонки (например
`users.inventory`), их надо применить обязательно; `•` — косметика.

## 5. Клиент Mini App

`miniapp/app.js` больше не привязан к захардкоженному домену: адрес API
вычисляется из `location.origin`, если страница открыта с `*.onrender.com`
(или localhost), иначе берётся `API_URL_FALLBACK`. Опечатка в домене
(`mppt`/`mptt`) больше не может сломать запросы к API.
