# Деплой AURA GAME: ровно два сервиса Render

Проект обслуживают **два** Web Service в Render. Третий (`dan4Bot-1`) удалён —
в коде нет ссылок на другие домены, а вся логика разложена так:

| Сервис | Что запускает | Чем занимается |
|---|---|---|
| **aura-api** | `uvicorn api:app --host 0.0.0.0 --port $PORT` | FastAPI: все игры, экономика, сундуки, магазин, апгрейд **и раздача Mini App** (`/miniapp` → `index.html`, `app.js`, `style.css`, картинки) |
| **dan4Bot** | `python bot.py` | aiogram (long polling): команды бота. Веб-сервер поднимается только формально (`start_fake_website`), чтобы Render видел открытый порт |

Оба сервиса используют **одну и ту же базу Supabase**, поэтому баланс в боте и в
Mini App — это одна запись (`users.coins`), синхронизация не нужна.

---

## 1. aura-api (Web Service)

- **Build Command:** `pip install -r requirements.txt`
- **Start Command:** `uvicorn api:app --host 0.0.0.0 --port $PORT`
- **Health Check Path:** `/api/health`
- **Environment:**
  - `SUPABASE_URL`
  - `SUPABASE_KEY`
  - `BOT_TOKEN`
  - `MAINTENANCE_MODE=1` — включить техработы обратно (по умолчанию **выключены**:
    играют все; с `=1` играют только `ADMIN_IDS`, остальные видят экран
    «Технические работы» и получают 403 от API).
  - Апгрейд техработы **не открывают**: он отдельно закрыт списком `ADMIN_IDS`
    (`UPGRADE_ADMIN_ONLY = True` в `api.py`) — пока админы, потом флаг в `False`.
- **Адреса:**
  - Mini App: `https://aura-api-mptt.onrender.com/miniapp/`
  - Корень `/` делает 307-редирект на `/miniapp/`
  - API: `https://aura-api-mptt.onrender.com/api/...`

Статика монтируется в `api.py`:

```python
BASE_DIR = os.path.dirname(os.path.abspath(__file__))
MINIAPP_DIR = os.path.join(BASE_DIR, "miniapp")
app.mount("/miniapp", StaticFiles(directory=MINIAPP_DIR, html=True), name="miniapp")
```

CORS открыт (`allow_origins=["*"]`): в WebView Telegram Origin бывает
`https://web.telegram.org`, `t.me` или отсутствует. Куки не используются —
авторизация только через подписанный `initData`.

## 2. dan4Bot (Web Service)

- **Build Command:** `pip install -r requirements.txt`
- **Start Command:** `python bot.py`
- **Environment:**
  - `BOT_TOKEN`
  - `SUPABASE_URL`
  - `SUPABASE_KEY`
  - (необязательно) `KEEPWARM=1` — прогрев `aura-api` по таймеру (см. §3.9;
    по умолчанию прогрев только «по активности в боте», чтобы не выйти за
    750 бесплатных часов Render)
  - (необязательно) `KEEPWARM_INTERVAL=240` — период прогрева, секунд
  - (необязательно) `KEEPWARM_SELF=1` — самопинг бота, чтобы он не засыпал
    (нужен `RENDER_EXTERNAL_URL` или `AURA_SELF_URL`)
  - (необязательно) `AURA_API_URL` — по умолчанию `https://aura-api-mptt.onrender.com`
  - (необязательно) `AURA_WEBAPP_URL` — по умолчанию `AURA_API_URL + "/miniapp/"`
  - (необязательно) `MINIAPP_SHORT_NAME` — короткое имя из BotFather (по умолчанию `Auragame`)
  - (необязательно) `MINIAPP_URL` — если нужно жёстко задать прямую ссылку `t.me/<бот>/<short_name>`
  - (необязательно) `BOT_USERNAME` — имя бота без `@`; по умолчанию берётся у Telegram при старте
  - Render сам добавляет `PORT` — его слушает `start_fake_website`

## 3. BotFather

`Configure Mini App` → **Web App URL** должен быть
`https://aura-api-mptt.onrender.com/miniapp/` (то есть `WEBAPP_URL` из `bot.py`).
`short_name` (`Auragame`) даёт прямую ссылку `https://t.me/<ваш_бот>/Auragame`.

**Команд `!апка` и `!апгрейд` больше нет (задача 20):**

Mini App открывается только кнопкой меню бота (BotFather → `Configure Mini App`),
а не командой в чате. Внутри бота ссылка собирается так же безопасно:

1. В личке — кнопка `web_app` с адресом `miniapp_webapp_url()` (это
   `https://aura-api-mptt.onrender.com/miniapp/`). Telegram открывает приложение
   сам и передаёт `initData`; короткое имя тут не участвует.
2. В группе Telegram **запрещает** кнопки `web_app`, поэтому там годится
   кнопка-ссылка `t.me/<бот>/<short_name>` — она открывает Mini App **внутри
   Telegram**, а не в браузере. `<бот>` подставляется из `get_me()` при старте.

Прямую ссылку `…onrender.com/miniapp/` игрокам отправлять нельзя: вне Telegram
не передаётся `initData`, и человек видит «технические работы» или пустой экран.
Ссылка `t.me/…` осталась только в админском `!сервисы` («Ссылка для игроков»).

Если в BotFather `short_name` не `Auragame` — задайте `MINIAPP_SHORT_NAME` в
сервисе dan4Bot или `MINIAPP_URL` целиком; перезапуск бота применит значение.

## 3.1. Если видите «Not Found»

`Not Found` — это ответ 404. Ниже все места, где он раньше появлялся, и что теперь:

| Что было не так | Было | Стало |
|---|---|---|
| В BotFather указан корень сервиса (без `/miniapp/`) | `Not Found` | 307 → `/miniapp/` |
| В BotFather указан `/index.html`, `/app.js`, `/style.css` | `Not Found` | 307 → `/miniapp/<файл>` |
| В BotFather указан адрес сервиса **dan4Bot** | `Not Found` | редирект в Mini App на aura-api |
| Имя Web Service в Render ≠ адреса в коде (`aura-api-mppt` / `aura-api-mptt`) | Render отвечает 404 на весь домен | клиент сам находит живой `/api/health`, бот на старте пишет рабочий адрес в лог |
| Запрос к `/api/...` несуществующего сервиса | `{"detail":"Not Found"}` | то же, но в `!сервисы` видно «❌ 404 Not Found» и подсказка про `AURA_API_URL` |
| Открыли `/webapp`, `/main` и т.п. | `Not Found` | 404 с подсказкой: где Mini App, где `/api/health`, где `/api/docs` |

Проверка адресов (в браузере или терминале):

```bash
curl -s https://<сервис>.onrender.com/api/health        # {"ok":true,"service":"aura-api",...}
curl -sI https://<сервис>.onrender.com/                 # 307 → /miniapp/
curl -sI https://<сервис>.onrender.com/index.html       # 307 → /miniapp/index.html
```

В боте (админ): `!сервисы` — покажет `✅ онлайн` или `❌ 404 Not Found` с причиной.
Если нужного домена нет в коде — задайте переменную `AURA_API_URL` в сервисе dan4Bot,
перезапуск не требуется для клиента: он всё равно возьмёт origin страницы `/miniapp/`.

## 4. Как проверить, что всё на двух сервисах

1. В боте (админ): `!сервисы` — покажет статус `aura-api` (`/api/health`),
   адрес API, адрес Mini App и подтверждение, что второй сервис — сам бот.
2. В браузере: `https://aura-api-mptt.onrender.com/api/health` →
   `{"ok": true, "status": "alive", "service": "aura-api", ...}`.
   То же самое отдаёт короткий алиас `/health` и `/` — их удобно ставить
   в UptimeRobot (см. §3.10).
3. `https://aura-api-mptt.onrender.com/miniapp/` — открывается Mini App
   (без Telegram покажет экран техработ: `initData` отсутствует — это норма).
4. `https://aura-api-mptt.onrender.com/` — в браузере редирект на `/miniapp/`,
   а для монитора (`Accept: */*`, так ходит UptimeRobot) — тот же
   `{"ok": true, "status": "alive", ...}`.

## 3.9. «SERVICE WAKING UP / START BUILDING ON RENDER TODAY» вместо игры

**Что это.** Это **страница самого Render**, а не наш код и не Mini App. Так
выглядит **просыпающийся** бесплатный Web Service: Render усыпляет free-инстанс
после **15 минут без входящих запросов**, а первый запрос ждёт ~1 минуту. Всё это
время браузер/Telegram показывает этот экран — до нашего `index.html` дело не
доходит.

Проверить причину за 5 секунд: открыть `https://aura-api-mptt.onrender.com/api/ping`.

- ответ сразу → сервис спит/не спит видно по `uptime_seconds` (маленькое число =
  только что проснулся);
- ответ через ~минуту → сервис спал. Это не баг, это лимит тарифа.

**Что уже сделано в коде (бесплатно, без правок настроек):**

| Механизм | Когда работает | Что даёт |
|---|---|---|
| `/api/ping` в `api.py` | всегда | дешёвый эндпоинт прогрева (ни базы, ни тиража) |
| `WarmApiMiddleware` в `bot.py` | любое действие в боте | бот будит `aura-api` **до** того, как игрок откроет Mini App |
| сердцебиение в `app.js` | пока аппка открыта | пинг каждые 4 минуты: сервис не успевает уснуть между экранами |

Строка `!сервисы` → «♻️ Прогрев: ✅ aura-api отвечал N с назад» показывает, что
механизм реально работает.

**Если экран всё ещё вылезает** — значит сервис спал, пока в боте было тихо.
Тогда есть три варианта:

1. **Держать `aura-api` тёплым постоянно (бесплатно).** Внешний cron
   (cron-job.org, UptimeRobot, GitHub Actions) раз в 5 минут запрашивает
   `https://aura-api-mptt.onrender.com/api/ping`. Это ~730 инстанс-часов в месяц
   из 750 бесплатных — влезает.
2. **Таймер из бота:** в `dan4Bot` добавить `KEEPWARM=1` (интервал —
   `KEEPWARM_INTERVAL=240`). Минус: пока бот живёт, он держит и API, а два
   всегда-включённых сервиса — это ~1460 ч/мес, то есть **выход за 750
   бесплатных часов** и приостановка сервисов до 1 числа. Поэтому по умолчанию
   выключено.
3. **Платный инстанс** ($7/мес, Starter) у `aura-api` — сон исчезает совсем.

Дополнительно: `KEEPWARM_SELF=1` заставляет бота пинговать самого себя
(`RENDER_EXTERNAL_URL`/`AURA_SELF_URL` + `/health`). Это лечит другую беду — «бот
молчит»: бот на long polling тоже усыпляется, потому что исходящие запросы к
Telegram Render за входящие не считает. Но по часам это тот самый вариант 2.

## 3.10. UptimeRobot: чтобы `aura-api` не засыпал (и не показывал «Down»)

Бесплатный Web Service на Render спит после **15 минут** без входящих запросов.
Внешний пинг раз в 5 минут держит сервис тёплым (~730 ч/мес из 750 бесплатных).
Подойдёт любой монитор с GET-запросами; ниже — UptimeRobot (бесплатный тариф
даёт 5-минутный интервал).

1. uptimerobot.com → **Add New Monitor**.
2. **Monitor Type**: `HTTP(s)`.
3. **Friendly Name**: `aura-api`.
4. **URL**: `https://aura-api-mptt.onrender.com/api/health`
   (подойдут также `/health` — тот же ответ, `/` — для монитора отдаёт этот же
   JSON, или `/api/ping` — ещё дешевле, без обращения к базе).
5. **Monitoring Interval**: `5 minutes`.
6. **Advanced → Keyword**: тип `exists`, значение `alive`.
   Так монитор краснеет не только когда сервис лежит, но и когда он отдаёт
   что-то постороннее.
7. **Create Monitor**.

Что должно быть в ответе:

```json
{"ok": true, "status": "alive", "service": "aura-api", "awake": {"uptime_seconds": 120, "just_woke": true}}
```

Важно: пинговать надо **тот сервис, который будит игрок**, — `aura-api`
(статика + API). Сам бот `dan4Bot` работает на long polling: его Render тоже
усыпляет, и лечится это либо `KEEPWARM_SELF=1` (§3.9, вариант 2), либо вторым
монитором на `https://<bot>.onrender.com/health`. Второй монитор = второй
всегда-живой сервис ≈1460 ч/мес, поэтому по умолчанию мы держим только
`aura-api`.

Если монитор показывает **Down** через минуту-две после создания — это не
ошибка: первый запрос будит инстанс, и UptimeRobot получает таймаут. Второй
запрос через 5 минут уже проходит.

## 4.0. Ошибка RLS при создании промокода

`new row violates row-level security policy for table "promocodes"` — в Supabase
включён RLS, а политик для серверной роли нет. Два способа лечения:

1. **Быстро, без правки базы:** добавить в сервисы `aura-api` и `dan4Bot`
   переменную `SUPABASE_SERVICE_KEY` = service_role key (Supabase → Settings → API).
   Код уже поддерживает её (`bot.py`, `api.py`).
2. **Миграцией:** применить `supabase/migrations/20261101000000_server_rls_policies.sql`
   (создаёт политики `*_server_all` для promocodes, promocode_uses, chest_claims,
   capsule_stock, upgrade_log, crash_history, bans) и выполнить
   `NOTIFY pgrst, 'reload schema';`.

Бот теперь показывает причину и подсказку прямо в чате, а не только в логах Render.

## 4.1. Сундуки: рулетка и «Сундуки обновляются»

**Анимация.** После нажатия «Открыть» сначала идёт белая вспышка ровно 1 секунда,
затем полоса предметов в стиле кейсов CS (`.roulette-container`): ячейки едут
справа налево ~6 секунд с плавным торможением, на каждой пройденной ячейке —
щелчок, по центру золотая метка. Выигрышная ячейка встаёт ровно под метку и
подсвечивается, ещё через 0.7 с открывается окно «Забрать». Награда начисляется
только по кнопке «Забрать» (`/api/claim_chest`), до этого баланс не меняется.

**Обычная капсула из сундука (задача 22).** Кроме коинов и ключа сундук может
выдать 💊 обычную капсулу — отдельным броском, **в добавок** к остальной награде:

| Сундук | Шанс капсулы | Откуда берётся |
|---|---|---|
| Обычный | **0.1 %** | `CHEST_CAPSULE_CHANCE_NORMAL` в `api.py` |
| Золотой | **10 %** | `CHEST_CAPSULE_CHANCE_GOLD` в `api.py` |

Клиент те же числа держит в `CHEST_CAPSULE_CHANCE_NORMAL/GOLD` в `miniapp/app.js`
(по ним рисуется лента рулетки) и печатает шанс под карточкой сундука. Проверить
можно по `/api/health` → `chests.normal.capsule_chance` / `chests.gold.capsule_chance`,
а в боте — `!сервисы` (строка «💊 капсула: обычный 0.1%, золотой 10%»).
Капсула, как и коины, начисляется **только по кнопке «Забрать»**.

> Чтобы капсула переживала перезапуск Render, примените
> `supabase/migrations/20261108000000_chest_capsule_reward.sql` (колонки
> `reward_item`, `reward_item_amount` + новые `chest_claim_*`). Без неё игра
> работает: капсула ждёт «Забрать» в памяти процесса и **пропадёт**, если сервис
> перезапустится до нажатия кнопки.

**Сундук открывается даже при сломанной таблице, но награда всё равно ждёт кнопку.**
Если `chest_claims` недоступна (нет таблицы, включён RLS, устарел кэш PostgREST),
сервер не отвечает 503 и **не начисляет коины сразу**: награда кладётся в память
процесса под id вида `mem-1a2b3c4d5e6f` и выдаётся тем же `/api/claim_chest`.
Ни при каком сценарии баланс не меняется до нажатия «Забрать». В логах:

```
ОШИБКА СУНДУКА: chest_claims недоступна → награда ждёт «Забрать» в памяти user_id=…: …
СУНДУК: награда отложена в памяти user_id=… claim=mem-1a2b3c4d5e6f (+13 коинов, +0 ключей)
СУНДУК: награда забрана из памяти user_id=… +13 коинов, +0 ключей
```

> Ограничение: память живёт до перезапуска Render (`TTL 12 часов`). Если награда
> ещё не забрана, а сервис перезапустился, `/api/claim_chest` ответит `404
> «Награда не найдена (сервер перезапускался). Открой сундук ещё раз»`. Поэтому
> таблица `chest_claims` остаётся основным путём — миграции обязательны.

Чтобы вернуть правильную схему «награда только по кнопке Забрать», примените обе
миграции и перезагрузите кэш схемы:

```sql
-- Supabase → SQL Editor
-- 20261030000000_capsule_stock_promo_types.sql   (сама таблица chest_claims)
-- 20261102000000_stock_and_chest_rpc.sql         (функции chest_claim_*: работают и при RLS)
NOTIFY pgrst, 'reload schema';
```

Проверить: `https://<сервис>/api/chest_ready` (или `!сервисы` в боте) — поле
`rpc_ready: true` означает, что функции на месте и награда снова выдаётся по «Забрать».

## 4.2.0. Тираж ВКЛЮЧЁН: все капсулы лимитированные

Задача 19: в `shop_catalog.py` стоит

```python
STOCK_LIMITS_ENABLED = True    # False — вернуть «бесконечные» капсулы
```

Тиражи (общие на всех игроков, `total_limit` в `SHOP_ITEMS`):

| Капсула | id | Тираж |
|---|---|---|
| Обычная 💊 | `capsule` | 1000 |
| Уникальная ⚱️ | `uniq_capsule` | 500 |
| Рубиновая ♦️ | `ruby` | 100 |
| Алмазная 💎 | `diamond` | 50 |
| Галактическая 🌌 | `galactic` | 10 |

Дневные лимиты выключены отдельным флагом `DAILY_LIMITS_ENABLED = False`:
ограничение только общим тиражом, «лимит N/день» нигде не показывается.
Включить обратно — поставить `True` и перезапустить `aura-api` + `dan4Bot`.

Что это значит на практике:

- в карточке магазина снова есть «Осталось: X из Y»;
- тираж списывается **до** баланса одной атомарной SQL-функцией
  `shop_take_stock` (SECURITY DEFINER), поэтому две одновременные покупки не
  продают одну капсулу дважды;
- когда строка тиража кончается (`stock = 0`), карточка исчезает с витрины, а
  покупка отвечает `400 Товар распродан`; если распродано ВСЁ, витрина пишет
  «Всё распродано», а не «Магазин пуст»;
- если записать тираж не удалось (нет миграции / RLS), магазин **не врёт**:
  покупка проходит, но в ответе `stock_ready: false`, `stock_warning` и в карточке
  «Остаток уточняется» — цифру полного тиража вместо реального остатка больше
  не покажем;
- при первом же чтении стока (`/api/shop_items`, `/api/health`, покупка) сервер
  сам добивает недостающие строки тиража (`shop_stock_snapshot` →
  `ensure_stock_rows`), поэтому «нет строки → распродан» больше не случается.

### 4.2.0.1. Что применить в Supabase (один файл, можно повторно)

```
supabase/migrations/20261106000000_stock_limits_on.sql
```

Он создаёт таблицу `capsule_stock`, добивает строки всех пяти капсул, приводит
`total` к тиражам каталога (проданное не возвращает — `stock` только обрезается
до `total`), пересоздаёт `shop_take_stock` / `shop_return_stock` /
`shop_stock_list` с `SECURITY DEFINER`, удаляет старую одноаргументную версию
`shop_take_stock`, выдаёт гранты и политику RLS, печатает таблицу остатков и
делает `NOTIFY pgrst, 'reload schema'`.

Проверка после деплоя:

1. `https://<сервис>/api/health` → `shop_stock.limits_enabled: true`,
   `shop_stock.ready: true`, `shop_stock.left` с ненулевыми остатками,
   `shop_stock.missing_rows: []`;
2. `https://<сервис>/api/stock_debug` → видно, какая сигнатура RPC отвечает и что
   лежит в таблице;
3. в боте (админ): `!сервисы` → строка «🎟️ Тираж: ✅ …», `!магазин` → у каждой
   капсулы «осталось X из Y»;
4. покупка в Mini App уменьшает счётчик на 1, при остатке 1 после покупки
   карточка исчезает.

**Открытие игры для всех (задача 21):** `MAINTENANCE_MODE` по умолчанию
выключен — играют все, апгрейд остаётся только за админами. Тиражи к открытию
обнуляются файлом `supabase/migrations/20261107000000_open_launch_promo_rls_and_stock_reset.sql`
(он же лечит RLS у `promocodes`: ошибка `42501 new row violates row-level
security policy for table "promocodes"`). Там же витрина стала одинаковой для
всех: `ruby`, `diamond`, `galactic` больше не `admin_only` — обычный игрок видит
все 5 капсул с тиражами.

**Если счётчик не двигается:** почти всегда не применён
`20261106000000_stock_limits_on.sql` (нет RPC или RLS режет `UPDATE`). В логах
Render это видно строкой `ОШИБКА СТОКА: RPC вернула «распродано», но в таблице …`
или `МАГАЗИН: ВНИМАНИЕ тираж не списан (stock_ready=false)`.


## 4.2. Тираж капсул: «Осталось: 1000 из 1000» не меняется

**Почему так было.** Продажа шла, а `UPDATE capsule_stock` падал (RLS или строки нет),
и ошибка глоталась: сервер считал, что списание прошло. Каталог при этом отдавал
полный тираж — отсюда «1000 из 1000» после покупки 30 капсул.

### 4.2.1. «Осталось: 1 000 из 1 000», а покупка → «Товар распродан»

**Симптом.** Карточка уверенно показывает полный тираж, а на «Купить» приходит
`400 Товар распродан`.

**Причина.** В `capsule_stock` **нет строки** для предмета (сид не применяли, строку
удалили, `INSERT` режет RLS). Каталог подставлял вместо остатка полный тираж —
`stock = total`, — а `shop_take_stock` строки не находил и возвращал `-1`
(«распродан»). Одно и то же отсутствие строки давало два противоположных сообщения.

**Лечение (одна команда, можно применять повторно):**
`supabase/migrations/20261106000000_stock_limits_on.sql` — создаёт таблицу, добивает
недостающие строки тиража (`ON CONFLICT DO NOTHING`: проданное не возвращается),
пересоздаёт `shop_take_stock` / `shop_return_stock` / `shop_stock_list`
с `SECURITY DEFINER`, выдаёт гранты и политику RLS и делает `NOTIFY pgrst`.

**Что изменилось в коде:**

- остаток считается известным только при наличии строки: `stock_ready=false`
  вместо фальшивого «1 000 из 1 000», в карточке — «Остаток уточняется»;
- на покупке `-1` от функции больше не означает «распродан» автоматически:
  сервер перечитывает таблицу, при отсутствии строки создаёт её и повторяет списание;
  «Товар распродан» отдаётся только когда в таблице действительно `0`;
- если списать так и не удалось (RLS/нет таблицы), покупка проходит, но ответ
  содержит `stock_ready=false` и `stock_warning`, а клиент перестаёт показывать
  число остатка до перезапуска аппки (иначе оно врёт);
- `/api/health` → `shop_stock.missing_rows` и `shop_stock.hint` называют, каких
  строк нет и какую миграцию применить; `!сервисы` в боте пишет то же самое.

**Что теперь.** Списание — одна атомарная SQL-функция `shop_take_stock` из миграции
`supabase/migrations/20261102000000_stock_and_chest_rpc.sql`:

```sql
UPDATE capsule_stock SET stock = stock - 1 WHERE item_id = … AND stock > 0 RETURNING stock;
```

Функция `SECURITY DEFINER`, поэтому работает даже когда RLS на таблице включён,
а сервис ходит ключом `anon` (service-role ключ не обязателен).

**Сигнатура функции (версия 20261103).** Сервер вызывает её так:

```python
supabase.rpc("shop_take_stock", {"p_item_id": "capsule", "p_amount": 1}).execute()
```

Функция объявлена как `shop_take_stock(p_item_id text, p_amount integer DEFAULT 1)`,
поэтому работают оба вызова — с `p_amount` и без него. Возвращает остаток после
списания (`0` — продан последний экземпляр), `-1` — распродан, `-2` — нет таблицы.
Код понимает и `boolean`-контракт (`True`/`False`), если функция написана так.

> Если вы применяли только `20261102000000_stock_and_chest_rpc.sql` (функция с одним
> параметром), PostgREST отвечал `PGRST202` на вызов с `p_amount`, и списание уходило
> в старый путь с `UPDATE`. Примените `supabase/migrations/20261103000000_shop_take_stock_amount.sql`
> и выполните `NOTIFY pgrst, 'reload schema';`.

**Как проверить, что транзакция прошла** — логи `aura-api` в Render, одна строка на
покупку:

```
СТОК capsule: rpc shop_take_stock{'p_item_id': 'capsule', 'p_amount': 1} → 999 ('ok')
МАГАЗИН: куплено user_id=… item=capsule баланс→9900 остаток→999 stock_ready=True
```

Когда тираж только что завели, в логе видно самолечение (строк не было — создали
и списали со второй попытки):

```
СТОК capsule: rpc shop_take_stock{'p_item_id': 'capsule', 'p_amount': 1} → -1 ('sold_out')
СТОК: созданы недостающие строки тиража ['capsule', 'uniq_capsule', …]
СТОК capsule: повтор {'p_item_id': 'capsule', 'p_amount': 1} → 999 ('ok')
```

А это — тот самый баг, если миграцию ещё не применили (покупка проходит, остаток
не ведётся):

```
ОШИБКА СТОКА: capsule нет строки в capsule_stock — примените …/20261106000000_stock_limits_on.sql
МАГАЗИН: ВНИМАНИЕ тираж не списан (stock_ready=false) item=capsule — …
```

Если функция недоступна, в логе будет `RPC shop_take_stock не найдена — списываем
условным UPDATE (старая схема)`, а при запрете записи — `ОШИБКА СТОКА: …`.

**Быстрая диагностика без логов:** откройте в браузере
`https://<сервис>/api/stock_debug` — там видно:

- `rpc_ready: true` — функция найдена и отвечает;
- `attempts[].params` — какая сигнатура сработала (`p_item_id` + `p_amount`);
- `attempts[].verdict: "sold_out"` на пробном id — правильный ответ (списывать нечего);
- `snapshot` — остаток, который сейчас видит магазин;
- `build` — версия кода; если в `/api/health` стоит старый `build`, значит Render ещё
  не задеплоил ветку `main`.

Пробный вызов безопасен: он идёт с несуществующим `item_id` (`__probe__`) и ничего
не списывает.

Если вместо этого видно:

```
ОШИБКА СТОКА: списание capsule через RPC: …
```
— значит функция не найдена/база отказала; покупка при этом не отменяется, но клиент
перестаёт показывать «Осталось: X из Y» (число скрывается, чтобы не врать), а
`!сервисы` пишет строку «🎟️ Тираж: ❌ …».

**Проверки без бота:**

1. `https://<сервис>/api/health` → блок `"shop_stock": {"ready": true, "left": {"capsule": 999, …}}`,
   а `missing_rows` должен быть пустым списком. Если там есть id — строк тиража нет,
   примените `20261106000000_stock_limits_on.sql`.
2. Supabase → Table editor → `capsule_stock`: `stock` уменьшается после каждой покупки.
3. Купить последнюю капсулу: карточка исчезает из магазина, повторная покупка
   отвечает `400: Товар распродан`.

**Уже проданное до фикса не списалось.** Если капсулы покупались, пока сток не
уменьшался, скорректируйте остаток один раз вручную (Supabase → SQL Editor):

```sql
-- пример: продано 30 обычных капсул «в никуда»
UPDATE public.capsule_stock SET stock = GREATEST(0, stock - 30), updated_at = now()
WHERE item_id = 'capsule';
```

**Если функции нет вообще** (миграции не применены) код падает обратно на условный
`UPDATE … WHERE stock = <прочитанный остаток>` и пишет
`СТОК capsule: списано 1, осталось 999 (без RPC)` — счётчик работает и так, но
атомарность гарантирует только SQL-функция. Когда RPC доступна, никакого `UPDATE`
таблицы не происходит: списание идёт одним вызовом функции (это проверяется тестом).

## 4.3. Апгрейд: стрелка и вердикт не расходятся

**Правило ровно одно, и оно одинаковое на сервере и на клиенте:**

| Бросок | Зона на круге | Итог |
|---|---|---|
| `roll < chance` | зелёная `0 → chance` | победа |
| `roll == chance` | сама граница (белая риска) | **победа** |
| `roll > chance` | красная `chance → 100` | проигрыш |

Стрелка и заливка считают угол **одной функцией** `upgradeAngleForPercent(%)`
(`% * 3.6`): `--p` круга, белая риска границы и позиция стрелки не могут разойтись.
У самой границы держится видимый зазор `0.6 п.п.` (2.16°): победа встаёт внутрь
зелёного, проигрыш — внутрь красного, поэтому «стрелка в красной зоне, а победа»
больше не встречается. Дальше зазора стрелка стоит ровно на броске.

Сервер (`api.py`, `upgrade_action`):

```python
chance_verdict = round(min(100.0, max(0.0, real_chance)), 2)   # ровно то, что уйдёт клиенту
roll = round(random.uniform(0.0, 100.0), 2)                    # 0.00..100.00
won = roll <= chance_verdict                                   # граница — победа
```

В ответе `chance` и `real_chance` — одно и то же число (`50.00`), лог `upgrade_log`
пишет его же, поэтому «сравнили с 47.5, а нарисовали 48» невозможно.

Клиент (`miniapp/app.js`):

- `upgradeRollWon(roll, chance)` → `roll <= chance` — та же граница;
- `upgradeArrowTargetFor` ставит стрелку на `roll * 3.6°`, но жёстко зажимает её в зону
  вердикта: при победе угол не может оказаться правее `chance`, при проигрыше — левее
  `chance`. Это односторонний зажим, а не «сдвиг только у самой границы», поэтому
  даже противоречивый ответ сервера не нарисует «стрелка в красном, а победа»;
- зазор у границы: `0.6 п.п.` (2.16°) внутри зелёного для победы и **пропорциональный**
  для проигрыша (`upgradeArrowRedClearanceDeg`). При шансе `99.99%` красная зона —
  всего `0.036°`, и фиксированный зазор вынес бы стрелку за 360°, то есть в ноль,
  обратно в зелёный. Теперь зазор не больше 60% красной зоны;
- `lockUpgradeChance()` фиксирует `--p` тем же числом, что пришло с сервера, ещё до
  остановки стрелки — зона и вердикт всегда про одно число;
- после остановки `finishUpgradeAnimation()` ещё раз доводит стрелку тем же расчётом:
  если анимацию прервали (повторный клик, уход с экрана), итоговый кадр всё равно
  показывает зону вердикта;
- белая риска `.up-boundary` крутится вместе с `--p` и показывает, где кончается
  зелёная зона;
- заливка круга теперь ставится **из JS** (`upgradeRingGradientCss()` →
  `conic-gradient(from 0deg, …)`) тем же углом `% * 3.6`, поэтому даже устаревший
  `style.css` из кэша Telegram не может повернуть круг на 90° и «перекрасить»
  вердикт; в `index.html` добавлены `Cache-Control/Pragma/Expires` мета-теги;
- зелёная зона: `conic-gradient(from 0deg, #22c55e 0 var(--p), #ef4444 var(--p) 360deg)`.

> **Почему именно `from 0deg`.** В CSS у `conic-gradient` ноль — это 12 часов, то есть
> ровно тот же ноль, от которого считается стрелка (`rotate(0deg)` → вверх). Раньше в
> стилях стояло `from -90deg`: круг был повёрнут на 90°, и при шансе 50 % зелёным
> оказывался ВЕРХ круга вместо ПРАВОЙ половины. Из-за этого победа с броском 30 %
> рисовалась в красной зоне («на красном зашло»), а проигрыш с броском 80 % — в
> зелёной («на зелёном не может»). Вердикт при этом был правильный — врал именно
> визуал. Тест `test_upgrade_geometry.js` проверяет, что ноль заливки, риски и
> стрелки совпадает, и что цвет под стрелкой всегда равен вердикту.

**Если «стрелка в красной зоне, а засчитали победу»:** почти всегда это старый
`app.js` в кэше Telegram. С версии `?v=aura-9` сервер отдаёт `index.html` с
`Cache-Control: no-cache`, а скрипты кэшируются по номеру версии — при следующем
открытии аппки клиент получает актуальный код. Проверить логику без браузера:
`POST /api/upgrade_action` (админ) — в ответе `roll`, `real_chance`, `won` должны
удовлетворять `won == (roll <= real_chance)`.

## 4.3.1. Дом-эдж апгрейда: на балансе 1000+ проигрыши чаще

Задача 18: «проигрыши должны случаться чаще, но визуал обязан оставаться честным».

```
api.py:   UPGRADE_HOUSE_EDGE_MIN_BALANCE = 1000
          UPGRADE_HOUSE_EDGE_FACTOR      = 0.8
```

- баланс **< 1000** → реальный шанс равен расчётному (`edge = 1.0`);
- баланс **≥ 1000** → реальный шанс = расчётный × `0.8` (50 % → 40 %, 10 % → 8 %);
- `edge` считается **внутри** цикла повторов, по только что прочитанному балансу
  (`raw_coins`), поэтому после каждого списания/выплаты он пересчитывается;
- на клиенте те же константы (`UPGRADE_HOUSE_EDGE_MIN_BALANCE`,
  `UPGRADE_HOUSE_EDGE_FACTOR`) и та же проверка по текущему балансу, поэтому круг,
  зелёная зона и подпись «ШАНС УСПЕХА» показывают **боевой** шанс (40 %), а не
  рекламный (50 %);
- в ответе `/api/upgrade_action`: `chance = real_chance` (по нему считался вердикт),
  плюс `advertised_chance` (без эджа) и `house_edge` — только для диагностики;
- после ответа клиент всё равно перерисовывает `--p` серверным числом
  (`lockUpgradeChance`), так что даже при рассинхроне баланса стрелка и зелёная
  зона не могут разойтись с вердиктом.

Что проверить в логе `upgrade_log` / `upgrade_history`:

```
chance 40.00   roll 41.37   won false   coins_before 1200   ← эдж сработал (0.8)
chance 50.00   roll 22.10   won true    coins_before  640   ← баланс < 1000, без эджа
```

Отключить эдж — поставить `UPGRADE_HOUSE_EDGE_FACTOR = 1.0` в `api.py` **и** в
`miniapp/app.js` (числа обязаны совпадать, иначе снова «зона ≠ вердикт»).

## 4.3.2. Лидерборд: только список игроков

Вкладка «Топ» — это заголовок «🏆 Топ игроков» и строки вида
**место | имя | баланс 💎**. Таймер сезона, призовые места, кнопка «?» и модалка
с описанием призов из интерфейса **убраны**.

`/api/season_end` остался в API (для совместимости и внешних запросов): он
отдаёт `end_timestamp` для **02.11.2026, 17:00 МСК** (`2026-11-02T14:00:00Z`) и
`timezone: "Europe/Moscow"`. Время задаётся с явной зоной: Render живёт в UTC, и
наивный `datetime` сдвигал бы конец сезона на 3 часа. Клиент этот эндпоинт
больше не вызывает, поэтому дату окончания сезона нигде не показывает —
если понадобится, берите её из ответа API.

## 5. Клиент Mini App

`miniapp/app.js` больше не привязан к захардкоженному домену: адрес API
вычисляется из `location.origin`, если страница открыта с `*.onrender.com`
(или localhost), иначе берётся `API_URL_FALLBACK`. Опечатка в домене
(`mppt`/`mptt`) больше не может сломать запросы к API.
